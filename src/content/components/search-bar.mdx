Open almost any app and the first thing you see is a grey field with a magnifying glass: *Search Amazon*, *Dishes, restaurants*, *Search in mail*. It's often the most used control in the whole app, and users expect it to behave exactly like the one in every other app.

It's also deceptively complex. Behind that one field sit the keyboard, suggestions, recent searches, a clear button, a Cancel button and focus handling. This page is about **the field itself**. What happens *after* you search (results, filters, sorting, debounce and race conditions) is covered on the [Search, filters & sorting](/features/search-filters-and-sorting) page.

## What is a search bar?

A search bar is a **single-line text field that takes a query and finds matching content**. It looks like a <Term id="text-field" />, but it behaves differently: what you type is a question to the app, not data to be saved.

Search bars work in one of two ways, and testers must know which one they're looking at:

- **Live filtering**: the list below updates as you type (contacts, settings, a list of 50 recipes). No Search key needed.
- **Submit search**: you type, optionally pick a suggestion, then press **Search** (Enter) and the app asks the server (shops, maps, mail).

Many apps mix the two: they show **suggestions** and **recent searches** while you type, and real **results** after you submit.

### How it differs from similar components

| Component | You type… | You get… |
| --- | --- | --- |
| **Search bar** | A free-text query | Results, matching or partly matching |
| **Text field** | Data to save (name, email) | Validation, then the value is stored |
| **Combo box** | Part of an option's name | One option from a fixed list (see [Dropdown](/components/dropdown)) |
| **Filter chips** | Nothing, you tap | A narrower list, by fixed categories |

<Callout type="dev" title="Platform names">
iOS has **UISearchBar** (usually inside a **UISearchController**) and SwiftUI's `.searchable`. Material 3 has a **search bar** that opens a **search view**. On the web it's `<input type="search">` inside a form marked with `role="search"` (or the newer `<search>` element). Users just say "the search box".
</Callout>

### Focus and the keyboard

The moment a user taps the field, a lot should happen at once, and each part is testable:

- **The keyboard opens** with a **Search** key instead of Return.
  <DevNote>On iOS that's the search return key type; on Android `imeOptions="actionSearch"`; on the web `type="search"` in a form, or `enterkeyhint="search"`.</DevNote>
- **Auto-capitalization and autocorrect are off.** A plain text field capitalizes the first letter and "corrects" words. In a search field that turns *iphone* into *Iphone* and *airpods* into *airports*.
- **The screen switches into search mode**: on iOS the large title collapses and **Cancel** appears; in Material the bar expands into a full **search view**.
- **Recent searches** or suggestions appear while the field is still empty.
- **The Search key submits** the query and usually hides the keyboard, so the results are visible.

### Suggestions and recent searches

Suggestions (also called <Term id="autocomplete" />) are a list that pops up under the field, so they share the bugs of dropdowns: keyboard navigation, highlighted vs selected, clipped lists. The [Dropdown](/components/dropdown) page covers the listbox pattern in detail. Recent searches add their own rules:

- **Most recent first**, and **no duplicates**: searching "pizza" twice moves it to the top, it doesn't add a second row.
- **Treat variants as the same search**: "Pizza", "pizza" and "pizza " are one entry.
- **Each entry can be removed**, and removed entries stay gone.
- **They're private**: after logging out or switching accounts, the next user must not see them.
- **Blank searches are never saved.**

### Clear, Cancel, Back and Esc

| Action | What it should do |
| --- | --- |
| **Clear (×)** | Empty the field, clear its results, keep focus and the keyboard |
| **Cancel** (iOS) | Leave search mode, hide the keyboard, restore the screen exactly as it was |
| **Back** (Android) | First close the keyboard or search view, then navigate back |
| **Esc** (web) | Close the suggestions; in some browsers (Chrome, Safari) it also clears an `<input type="search">` |

<Callout type="tip" title="Ask early: live or submit?">
Before testing, find out whether results should update **while typing** or only **after Search**. If it's live, check the <Term id="debounce" /> and fast typing (see the [feature page](/features/search-filters-and-sorting)). If it's submit, the Search key and the suggestion list are your main targets.
</Callout>

## When to use it

A search bar is a good choice when:

- There's **more content than people can scroll through comfortably**: products, contacts, messages, settings.
- Users **know what they're looking for** and can name it ("ramen", "invoice March").
- Search is a **main task**: then keep the bar visible at the top, not hidden behind an icon.
- Content has many attributes, so a fixed set of filters can't cover every question.

## Common bugs

These are the bugs testers report most often in the search field itself.

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Search key does nothing** | You press Search/Enter, nothing happens; only tapping a suggestion works | High |
| 2 | **Clear (×) leaves stale results** | The field is empty but old results stay, or × closes the keyboard | Medium |
| 3 | **Auto-capitalization / autocorrect on** | "iphone" becomes "Iphone", "airpods" becomes "airports"; results are wrong or empty | High |
| 4 | **Spaces and case not handled** | "pizza " or "PIZZA" finds nothing, although "pizza" works | Medium |
| 5 | **Blank query accepted** | Pressing Search on an empty or spaces-only field shows everything or an error | Low–Medium |
| 6 | **Duplicate or leaked recents** | "pizza" three times, deleted entries come back, or the previous user's searches appear | Medium (High if private) |
| 7 | **Cancel doesn't restore the screen** | After Cancel the selected tab, filter or scroll position is reset | Medium |
| 8 | **Stale suggestions** | The list still shows suggestions for an older query | Medium |
| 9 | **Keyboard covers results** | After submitting, the keyboard stays open and hides the results | Medium |
| 10 | **Long text breaks the layout** | Long queries push the × or Cancel off-screen, or the results title overflows | Low |
| 11 | **Special characters break it** | Emoji, diacritics, `&`, `%` or `"` cause errors, wrong encoding or no results | Medium |

<Callout type="bug" title="Why #3 is so sneaky">
On a desktop browser you'll never see it: you type "iphone", the field says "iphone". On a real phone, the keyboard capitalizes the first letter, and if the search is case-sensitive, *every* search from a phone fails. Always test search on a **real device keyboard**, not only by pasting text or using a laptop keyboard with the <Term id="simulator" />.
</Callout>

## Accessibility

- **A real label.** The placeholder is not a label: it disappears and is often too light. Give the field an accessible name ("Search dishes and restaurants"), and on the web mark the form as a search landmark so screen reader users can jump to it.
  <DevNote>The name comes from a visible label or `aria-label`; the landmark is `role="search"` (or `<search>`).</DevNote>
- **Icon buttons need names.** The × must be announced as "Clear text", the microphone as "Voice search", the filter as "Filters", never just "button".
- **Announce results.** After searching, screen reader users need to hear "12 results" or "No results".
  <DevNote>On the web that's a polite `aria-live` region; on mobile an accessibility announcement.</DevNote>
- **Suggestions** follow the combobox pattern: arrow keys to move, Enter to choose, Esc to close (see [Dropdown](/components/dropdown)).
  <DevNote>`role="combobox"` on the input, `role="listbox"` and `role="option"` for the list.</DevNote>
- **Focus management.** Opening a search view moves focus into the field; closing it returns focus to where the user was (the search icon or bar). The <Term id="focus-order" /> must stay logical.
- **<Term id="touch-target">Touch targets</Term>:** the × and Cancel are small; their tap area should still be at least 44×44 pt (iOS) / 48×48 dp (Android). On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px; 44×44 px (2.5.5, AAA) is the comfortable target.
- **Contrast:** typed text needs 4.5:1. Light grey placeholders often fail; if the placeholder carries information, it needs enough contrast too (<Term id="wcag" />).
- **Voice input** is an accessibility feature: dictated text must work like typed text (no trailing period, no capital letter breaking the search).

## Mobile vs web

<Tabs labels={['iOS', 'Android', 'Web']}>
<Tab>

- Search sits in the navigation bar, often hidden under the large title until you pull down: check users can find it.
  <DevNote>`UISearchController` with a `UISearchBar` in the navigation bar, or SwiftUI's `.searchable`.</DevNote>
- Focus shows **Cancel** and optional **scope buttons**; Cancel must restore the previous state.
- Test the **Search key**, auto-capitalization and autocorrect on a **real device**, **Dynamic Type** at the largest sizes, and dictation.
- Check that scrolling the results dismisses the keyboard when the app is designed to.

</Tab>
<Tab>

- Material 3 **SearchBar** expands into a **SearchView** (full screen on phones, docked on tablets). Older apps use a search icon in the toolbar.
- The system **Back** gesture should first close the keyboard or the search view, not leave the screen.
- Check the keyboard's action key says Search and submits.
  <DevNote>The action key comes from `imeOptions="actionSearch"`.</DevNote>
- Test with **TalkBack**, **font scale**, different keyboards (Gboard, Samsung Keyboard) and **landscape**, where the keyboard can cover most of the screen.

</Tab>
<Tab>

- Some browsers add their own × to a search field and clear it on Esc (Chrome and Safari do; behavior and styling differ between browsers), so check it doesn't clash with the site's own ×.
  <DevNote>Use `<input type="search">` with a `<label>`, inside a form with `role="search"` or a `<search>` element.</DevNote>
- Watch for **two dropdowns at once**: the browser's autofill history on top of the site's own suggestions.
  <DevNote>Custom suggestions usually need `autocomplete="off"`.</DevNote>
- The query normally ends up in the URL (`?q=`), so Back, refresh and sharing should restore it. Encoding of `&`, `%`, `#` and emoji is a classic bug source. More in [Search, filters & sorting](/features/search-filters-and-sorting).
- Test keyboard-only use, mobile browsers (does the keyboard show "Go" or "Search"?), and narrow widths.

</Tab>
</Tabs>

<KeyTakeaways>

- A search bar is a text field for **queries**: it should never auto-capitalize or autocorrect, and it should ignore **case, accents and extra spaces**.
- Know whether it's **live filtering** or **submit search**; then test the **Search key**, the **×**, **Cancel / Back / Esc** and **focus** carefully.
- **Recent searches** must be newest first, **de-duplicated**, removable, free of blanks and **private** to each account.
- Suggestions are a listbox: test them like a [dropdown](/components/dropdown), with the keyboard and with fast typing.
- Always test on a **real phone keyboard**, with long text, emoji and diacritics, and with a screen reader.

</KeyTakeaways>
