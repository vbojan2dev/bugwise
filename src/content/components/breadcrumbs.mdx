You search an outdoor shop for "lantern" and open the Storm Lantern. Above the title it says **Home › Camping › Tents**. A lantern, filed under tents? You tap **Camping** to look around and get a "Page not found". Two clicks, two bugs, and you haven't even looked at the product yet.

Breadcrumbs are one line of small text, so nobody tests them on purpose. But every level is a **link that must work**, the trail is a **promise about the site's structure**, and on a phone the whole thing has to fit in about 330 pixels.

## What is it?

A **breadcrumb** is a row of links that shows where the current page sits in the site's hierarchy: **Home › Camping › Tents › Trailhead 2P Tent**. Each level is a link to a parent page, and the last item is the page you're on. It answers two questions at a glance: *Where am I?* and *How do I get one level up?*

The name comes from Hansel and Gretel, who dropped breadcrumbs to find their way home. You'll find breadcrumbs on web shops, documentation sites, help centers, government sites and admin tools: anywhere with a **deep hierarchy** of pages.

### Location-based or path-based?

There are two very different ideas behind the same-looking trail:

| Type | Shows | Example |
| --- | --- | --- |
| **Location-based** | Where the page **lives** in the site's hierarchy. Always the same for a page. | Home › Lighting › Lanterns › Storm Lantern |
| **Path-based** (history) | The pages the user **visited** to get here. Different every time. | Home › Search "lantern" › Storm Lantern |

**Location-based** is what people almost always mean by "breadcrumbs" and what you should expect. Path-based trails just repeat the browser's **Back** button, and they produce confusing results when users arrive from search, an email or another site. A third kind, **attribute-based**, shows the filters that narrowed a list (Tents › 2-person › Under $200); it often looks like a row of removable chips.

<Callout type="bug" title="The half-and-half bug">
Many breadcrumb bugs happen when a team *means* location-based but builds the trail from **session history**: "the last category the user browsed". The product then appears in a category it isn't in. That's exactly the lantern-under-tents bug from the introduction.
</Callout>

### A web pattern

Breadcrumbs belong to **websites** (desktop and mobile web). Native iOS and Android apps don't use them: the [navigation bar](/components/navigation-bar) shows a **back button** with the previous screen's title, and Android adds the system Back gesture. If you see a breadcrumb in a native app, it's usually a web view, or a design copied from the website. Test whether it still behaves like the app's back navigation.

## When to use it

- The site has a **hierarchy of three or more levels**: category › subcategory › product, or docs section › chapter › article.
- Users often **land deep** in the site from search engines, ads or shared links, and need a quick way up.
- Users want to **browse siblings**: from one tent, go up to *Tents* and compare.

## How good breadcrumbs behave

### They match the real hierarchy and the URL

The trail should mirror how the site is actually organized, and usually the URL too: `shop.example.com/c/camping/tents` → **Home › Camping › Tents**. Every level must open a real page (200, not a 404 or a redirect loop). When the catalog changes (a category is renamed, merged or moved), the breadcrumbs must change with it. Old category names in the trail are a classic sign of a stale cache or a hard-coded trail.

A product that lives in **several categories** (a lantern in *Lighting* and in *Camping › Essentials*) needs a rule: usually one **primary** category is always shown. What must never happen is a trail that shows a category the product **isn't in**.

### The current page is not a link

The last item shows where you are. A link to the page you're already on is useless at best; at worst it reloads the page, throws away what the user typed or scrolled, and adds a duplicate entry to the browser history. Expect plain text, marked with `aria-current="page"`.

### Long names and small screens

Real category names are long: "Outdoor & Camping Equipment", "Backpacking Tents (1–2 person)", and product names longer still. On a 360 px phone, a full trail can wrap over three lines and push the page title out of view. Good designs pick a strategy on purpose:

| Strategy | Watch out for |
| --- | --- |
| **Wrap** to several lines | Takes too much height; the trail looks like body text |
| **Collapse** the middle into "…" | The "…" must be a real button that reveals the hidden levels |
| **Parent only** ("‹ Tents") | Users lose the sense of depth; check it's the right parent |
| **Horizontal scroll** | Hidden levels are easy to miss; scroll position should start at the end |

Whatever the strategy, check the <Term id="truncation" />: a cut-off label needs the full text available somewhere (in the menu, a tooltip on desktop, or the page title).

### Filters and sorting

Breadcrumbs point to **category pages**, not to the exact list the user saw. That's normal, but many shops promise more: "the category level takes you back to the list as you left it". If the ticket says so, coming from `?people=2&sort=price` must keep that <Term id="query-parameter" />. Ask what was agreed, and test it.

### Structured data (SEO)

Web pages often describe their breadcrumb to search engines with a small block of JSON-LD (schema.org `BreadcrumbList`). Search engines can then show the trail in results instead of a raw URL:

```json
{
  "@context": "https://schema.org",
  "@type": "BreadcrumbList",
  "itemListElement": [
    { "@type": "ListItem", "position": 1, "name": "Camping", "item": "https://shop.example.com/c/camping" },
    { "@type": "ListItem", "position": 2, "name": "Tents", "item": "https://shop.example.com/c/camping/tents" },
    { "@type": "ListItem", "position": 3, "name": "Trailhead 2P Tent" }
  ]
}
```

As a tester, check that it **matches the visible trail** (same levels, same order, working URLs) and that Google's **Rich Results Test** reports no errors. A copied template that says "Shoes › Sneakers" on every page of an outdoor shop is a real bug.

## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Wrong category (stale path)** | A product appears under the category the user browsed last, not its own | Medium |
| 2 | **A level is a 404** | Clicking a level opens "Page not found" | Medium–High |
| 3 | **Current page is a link** | Clicking it reloads the page and adds a history entry | Low |
| 4 | **Separators read aloud** | Screen reader says "slash" between levels | Low–Medium |
| 5 | **Unreachable levels on phones** | "…" is not clickable, middle levels can't be reached | Medium |
| 6 | **Trail doesn't match the URL or menu** | Old category names, wrong order, missing level | Low–Medium |
| 7 | **Filters lost** | Category level drops the filters the ticket says it keeps | Low–Medium |
| 8 | **Layout breaks** | Long names overflow the screen or overlap the title | Medium |
| 9 | **Structured data mismatch** | Search results show a different trail than the page | Low |

### Tools

- **DevTools › Elements** (see [DevTools for testers](/web/devtools-for-testers)): check `<nav aria-label="Breadcrumb">`, the `<ol>`, `aria-current="page"` and that separators are CSS or `aria-hidden`.
- **DevTools › Network** or a link checker: click every level and confirm a **200** <Term id="http-status-code" />, not 404 or 301 → 301 → 301.
- **Device toolbar** (responsive mode) at 360 px with the longest category names you can find. See [responsive design testing](/web/responsive-design-testing).
- **Google Rich Results Test** or the Schema Markup Validator for the `BreadcrumbList` JSON-LD.
- **A screen reader**: VoiceOver on Mac (<kbd>Cmd</kbd>+<kbd>F5</kbd>), NVDA on Windows, TalkBack in Chrome on Android.

## Accessibility

- **Landmark and label.** Wrap the trail in `<nav aria-label="Breadcrumb">` so <Term id="screen-reader" /> users can jump to it, and so it's not confused with the main menu (another `nav`). This is the <Term id="aria" /> breadcrumb pattern.
- **An ordered list.** Put the levels in an `<ol>`. Screen readers then announce "list, 4 items", which tells users how deep they are.
- **Current page.** Plain text with `aria-current="page"`, read as "current page". Make it visually different too (bold, not a link color), not by color alone.
- **Separators are decoration.** Screen reader users shouldn't hear "slash" or "greater than" between every level.
  <DevNote>Use CSS (`::before` content, a background image) or `aria-hidden="true"`.</DevNote>
- **Icon-only Home** needs an accessible name. **Collapsed levels** need a real button with a name like "Show 2 more levels" and `aria-expanded`.
- **<Term id="keyboard-navigation">Keyboard</Term>.** Every link reachable with <kbd>Tab</kbd>, visible focus, <kbd>Esc</kbd> closes the "…" menu and returns focus to its button.
- **<Term id="touch-target">Touch targets</Term>.** At least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px; 44×44 px (2.5.5, AAA) is the comfortable target. Breadcrumb links are often 12 px text crammed together, so check the spacing between them on phones.
- **Contrast.** Links and the current page text need 4.5:1 for normal text; the separators are decorative, but keep them visible.

- A breadcrumb inside the app is usually a **web view**: test it with the web checks and make sure its links don't open a second copy of the app in a browser.

- Up (in the app bar) should go to the logical parent screen; Back goes to the previous screen. After a deep link they can differ, so test both.
- Large-screen apps (tablets, Chromebooks) sometimes show a breadcrumb-like path in file managers. Test long folder names and rotation.

<KeyTakeaways>

- Breadcrumbs show **where a page lives** in a hierarchy: Home › Category › Subcategory › Page. They're a **web** pattern; native apps use a back button.
- Expect **location-based** trails: the same for a page however the user arrived. Trails built from history put products in the wrong category.
- **Every level must work** (no 404s) and the **current page is plain text** with `aria-current="page"`.
- On phones, choose a strategy (wrap, collapse, parent only, scroll), and make sure **hidden levels stay reachable**.
- Markup: `<nav aria-label="Breadcrumb">`, an `<ol>`, and **separators hidden** from screen readers.
- Check the trail **matches the URL, menu and structured data**, and ask whether category links should keep **filters**.

</KeyTakeaways>
