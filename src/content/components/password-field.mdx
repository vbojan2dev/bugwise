Logging into your bank, creating an account in a food delivery app, confirming a payment, changing your password after a breach: the password field is the gate to almost every account. When it works, nobody notices. When it doesn't, users can't get in, and they blame themselves ("I must have forgotten it") before they blame the app.

A password field is a [text field](/components/text-field) with a few extra jobs: hide the value, let people reveal it, play nicely with password managers, and explain the rules. Each job has its own classic bugs. The bigger flow around it (generic error messages, lockout, sessions, reset links) lives on the [Login & sign up](/features/login-and-sign-up) page. This page is about **the field itself**.

## What is a password field?

A password field is a **single-line text field that masks what you type**, showing dots instead of characters. It's used for passwords, PINs typed on a keyboard, and other secrets like an API key or a card's security code.

It comes in two flavors, and they behave differently:

- **Current password** (login, confirm before deleting the account): the user types or autofills a password that already exists. It must accept it **exactly** as it was saved.
- **New password** (sign-up, change password, reset): the user invents one. The field shows the **rules**, maybe a **strength meter**, and password managers offer to **generate** one.

### How it differs from similar components

| Component | What's different | Typical use |
| --- | --- | --- |
| **Password field** | Masked, never autocorrected, managers fill it | Login, sign-up, change password |
| **[Text field](/components/text-field)** | Shows the value, may autocorrect | Name, email, notes |
| **One-time code field** | Digits only, often split boxes, SMS autofill | [2FA codes](/features/two-factor-authentication) |
| **PIN pad** | On-screen digits, fixed length | App lock, card PIN |

<Callout type="dev" title="Platform names">
iOS calls it a **secure text field** (`isSecureTextEntry` in UIKit, `SecureField` in SwiftUI). Android uses an `EditText` with `inputType="textPassword"`, or a Material `TextInputLayout` with a **password toggle**. On the web it's `<input type="password">`. Screen readers announce it as "secure text field" or "password".
</Callout>

## Designs & variants

The parts are the same everywhere; what changes is who helps the user. On iOS it's the **Passwords** app and its QuickType bar, on Android the **autofill service** (Google Password Manager or another manager), on the web the browser and extensions.

### Show / hide: small button, many details

Masking protects against someone looking over your shoulder, but it also hides typos. That's why almost every modern password field has a **show/hide toggle**. A good one:

- Has a **name** that says what it does ("Show password") and tells the **state**: either the name changes to "Hide password", or it's a toggle button with a pressed state. An icon alone says nothing to a <Term id="screen-reader" />.
  <DevNote>On the web: `aria-pressed`.</DevNote>
- **Keeps the value and the cursor position.** Tap it in the middle of typing and keep typing: the new characters must go where the cursor was, not to the start.
- **Keeps focus** in the field (on mobile, the keyboard shouldn't close and reopen).
- Goes back to **hidden** when the user leaves the screen or submits, so the password isn't still visible later.
- Has a big enough touch area: at least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px; 44×44 px (2.5.5, AAA) is the comfortable target.

<Callout type="warning" title="Two eyes in Microsoft Edge">
Edge adds its **own** reveal button to password fields. If the app draws a custom eye too, users see two. The fix is one line of CSS, but someone has to notice it first. Always open password forms in Edge during [cross-browser testing](/web/cross-browser-testing).

<DevNote>`::-ms-reveal`.</DevNote>
</Callout>

### Password managers and autofill

Many people never type their passwords: a <Term id="password-manager" /> fills them in. That only works if the field **tells the system what it is**, and if the app doesn't fight the manager.

| Field | Web `autocomplete` | iOS `textContentType` | Android `autofillHints` |
| --- | --- | --- | --- |
| Email / username | `username` | `.username` | `username` / `emailAddress` |
| Login password | `current-password` | `.password` | `password` |
| Sign-up / new password | `new-password` | `.newPassword` | `newPassword` |

What to check:

- **Login:** the saved password is offered (iOS QuickType bar, Android autofill dropdown, browser key icon) and fills **both** username and password.
- **Sign-up:** the system suggests a **strong password**, fills it in, and offers to **save** it with the right username.
  <DevNote>On iOS, apps can describe their rules with `passwordRules` so the suggestion actually passes them; on the web Safari reads the `passwordrules` attribute.</DevNote>
- **Paste works.** Users of password managers that don't autofill copy and paste. Blocking paste doesn't make anything safer; it pushes people to shorter passwords they can type. WCAG 2.2 criterion 3.3.8 Accessible Authentication (Minimum) (Level AA) expects login not to depend on remembering or retyping a password, and allowing paste and autofill is the usual way to meet it.
- **`autocomplete="off"` is a smell.** On password fields most browsers ignore it, some managers honor it, so behavior becomes unpredictable. It's never a security fix.
- **App and website share passwords** when they're linked: on iOS through Associated Domains, on Android through Digital Asset Links. A password saved on the website should be offered in the app.

### Rules, checklists and strength meters

Users can only follow rules they can see. Show them **before** the user types, then tick them off live. Error messages that reveal one rule at a time ("Needs a number." → "Needs a symbol." → "Too short.") are a classic usability bug.

Strength meters are trickier than they look. The common, naive version counts **character types**: lowercase, uppercase, digit, symbol. That's exactly what attackers expect. It rates `Password1!` as **Strong** (it's one of the first passwords any attacker tries) and a long passphrase like `sunflower meadow at dusk` as **Weak**. Current guidance, like NIST's SP 800-63B, favors **length** and checking against **lists of common and breached passwords** over composition rules.

<Callout type="tip" title="Ask early: what are the real rules?">
Get the rules in writing: minimum and maximum length, which characters are allowed (spaces? emoji? accented letters?), whether common passwords are blocked. Then check that sign-up, change password, reset and the server **all enforce the same rules**. Mismatches between them cause the nastiest bugs on this page.
</Callout>

### Length, spaces and other characters

- **Maximum length:** allow long passwords (64 characters or more is a common recommendation). If there's a maximum, **tell the user** and enforce it the same way on every form. A browser's `maxlength` cuts typed and **pasted** text without any message.
- **Silent <Term id="truncation" />:** if sign-up saves 20 characters but login only sends the first 16, the user is locked out with the right password. See <Term id="password-hashing" />.
  <DevNote>Some hashing algorithms (bcrypt) also only use the first 72 bytes.</DevNote>
- **Spaces:** a space is a valid password character. Trimming leading or trailing spaces is a team decision, but it must happen **the same way everywhere**, or "Secret123 " saved at sign-up won't match at login.
- **Unicode:** accented letters and emoji should work, and a password set on the web must work in the app. The keyboard on another device may produce a differently encoded "č".

### Caps Lock and other helpers

On computers, Caps Lock is the top reason for "I typed the right password". A web field can detect it while you type and show a warning. Safari on macOS shows its own Caps Lock indicator in password fields. Phones don't need this, their keyboards show the shift state.

<DevNote>`event.getModifierState('CapsLock')`.</DevNote>

### Keep the secret secret

A few security basics belong to the field itself:

- **Never in the URL or logs.** The password goes in a POST body, not in `?password=…`, and never into analytics events or crash logs. Check the network traffic with <Term id="devtools" /> or a [proxy tool](/mobile/proxy-tools).
- **No copy out of a masked field.** Browsers and the OS disable Copy and Cut while the value is hidden.
- **No autocorrect, no suggestions, no autocapitalize.** Otherwise the keyboard may learn the password and suggest it later.
- **Screenshots and screen recording** on sensitive screens: Android apps can block screenshots and recording and blank the app in the recent apps view. iOS has no switch to block screenshots; apps hide sensitive content when screen capture is detected and cover the screen in the app switcher.
  <DevNote>On Android that's `FLAG_SECURE` on the window.</DevNote>

## When to use it

A password field is the right choice when:

- The value is a **secret** that people nearby shouldn't see: password, PIN on a keyboard, recovery phrase, API key.
- The user must type it **again later** exactly as now, so a typo matters (that's why reveal is so useful).
- Password managers should **recognize** the field.

## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Silent truncation** | Sign-up accepts 20 characters, login cuts to 16: the right password never works | Critical |
| 2 | **Paste blocked** | Paste does nothing; password manager users can't log in | High |
| 3 | **Autofill broken** | No saved password offered, or the email lands in the password field | High |
| 4 | **Toggle without name or state** | Screen reader says just "button" | High (for affected users) |
| 5 | **Toggle moves the cursor** | After revealing, new characters go to the start, or the field is cleared | Medium |
| 6 | **Misleading strength meter** | `Password1!` is "Strong", a long passphrase is "Weak" | Medium |
| 7 | **Rules hidden until failure** | "Invalid password" with no hint, or one rule revealed per attempt | Medium |
| 8 | **Inconsistent rules** | Sign-up allows spaces or emoji, login or reset rejects them | High |
| 9 | **Spaces trimmed on one side only** | "Secret123 " saved at sign-up doesn't match at login | High |
| 10 | **Password leaks** | Visible in the URL, a log, an analytics event or the app switcher | Critical (security) |
| 11 | **Stays revealed** | Come back to the screen and the password is still in plain text | Medium |
| 12 | **Autocorrect on** | The keyboard "fixes" the password or suggests it later | Medium |

<Callout type="bug" title="Why #1 is so sneaky">
Each form works on its own. Sign-up with 20 characters: success. Log in with a short password: success. It only breaks when a **long password from one form meets the limit of another**. The user sees the generic "Email or password is incorrect" and assumes they forgot it. Test every password feature with the **same long password**, including emoji and spaces: sign-up, login, change, reset, and the app vs the website. That's <Term id="boundary-value-analysis" /> across forms.
</Callout>

## Accessibility

- **A real label:** "Password" or "New password", connected in code. Screen readers announce it as "secure text field" (iOS) or "password" (web, TalkBack) and don't read the characters aloud.
- **The toggle** needs a name and a state (WCAG 4.1.2 Name, Role, Value, Level A): "Show password" / "Hide password", or a pressed state. It should be reachable with <Term id="keyboard-navigation">Tab</Term> and work with Enter and Space.
  <DevNote>On the web the state is `aria-pressed`.</DevNote>
- **Autofill and paste** (WCAG 3.3.8 Accessible Authentication (Minimum), Level AA): don't make people memorize and retype. Mark the field's purpose so autofill works (also WCAG 1.3.5 Identify Input Purpose, Level AA).
  <DevNote>With `autocomplete`.</DevNote>
- **Rules and errors** are text, linked to the field, and announced. A live checklist should not spam the screen reader on every keystroke; the final state matters.
  <DevNote>Linked with `aria-describedby`.</DevNote>
- **Strength meters** must not rely on color alone: show the word ("Weak", "Strong") too. Text needs 4.5:1 contrast, the meter bars and field border 3:1 (WCAG 1.4.3 / 1.4.11).
- **<Term id="touch-target">Touch targets</Term>:** at least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px; 44×44 px (2.5.5, AAA) is the comfortable target.
- **No tight time limits** on typing a password; if there is a session timeout, warn before it ends.

## Mobile vs web

<Tabs labels={['iOS', 'Android', 'Web']}>
<Tab>

- There's **no built-in reveal button**: apps switch between a secure and a normal field, which is exactly where cursor and focus bugs come from.
  <DevNote>`UITextField` with `isSecureTextEntry = true`, or `SecureField` in SwiftUI.</DevNote>
- With Associated Domains, passwords saved for the website appear in the app.
  <DevNote>Set `textContentType` to `.username`, `.password` or `.newPassword`. Associated Domains use `webcredentials:`.</DevNote>
- **Strong Password** suggestions appear on new-password fields and should match the app's rules.
  <DevNote>They appear on `.newPassword` fields; `passwordRules` makes the generated password match the app's rules.</DevNote>
- The last typed character is shown briefly before it turns into a dot. That's normal.
- Test with the **Passwords** app and a third-party manager, **VoiceOver**, **Dynamic Type**, and the **app switcher** (does the screen hide sensitive content?).

</Tab>

<KeyTakeaways>

- A password field is a masked text field whose value must be accepted **exactly**, by every form that touches it.
- **Never cut a password silently.** Test the same long password (spaces, emoji, accents) on sign-up, login, change, reset, app and web.
- **Password managers** need `current-password` / `new-password` (and the iOS and Android equivalents) and **working paste**.
- Show/hide needs a **name, a state**, and must keep **value, focus and cursor**.
- Show **rules up front** and be wary of **strength meters** that only count character types.
- The password never belongs in a **URL, log or screenshot**.
