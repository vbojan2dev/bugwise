You're shopping for a tent. You scroll to the bottom of page 1, tap **2**, and the first tent on page 2 is... the last tent from page 1. You open a promising one on page 3, press **Back**, and you're on page 1 again. You give up and buy somewhere else.

Pagination looks like a row of small numbers. Underneath, it's **arithmetic** (which items belong on page 3?), **state** (where was the user?) and **boundaries** (page 1, the last page, page 0, page 999). Those three are exactly where testers find bugs.

## What is it?

<Term id="pagination">Pagination</Term> splits a long list (products, search results, orders, transactions) into **pages** that load one at a time. The user moves with **Previous / Next** and **page numbers**. Pages keep each request small and fast, and give users a sense of *where they are*: page 5 of 16.

You'll meet it in web shops and search results, bank transaction histories, admin tables, and in the API behind almost every list in a mobile app, even when the app hides it behind a "Load more" button or <Term id="infinite-scroll" />.

### Numbered pages, "Load more" or infinite scroll?

There are three common ways to reveal the rest of a long list. Each one is valid in the right place. Switch between them and try to reach the footer:

<PatternsCompare client:visible />

| Pattern | Best for | Watch out for |
| --- | --- | --- |
| **Numbered pages** | Search results, shops, tables, anything users compare or come back to | Tiny targets on phones, wrong page math |
| **"Load more" button** | Mobile lists, product grids | Losing loaded items and position after Back |
| **Infinite scroll** | Social feeds, photo streams, "just browsing" | Unreachable footer, no sense of position, memory, accessibility |

<Callout type="info" title="It's pagination underneath anyway">
"Load more" and infinite scroll still fetch **pages** from the server (`?page=2`, `?cursor=abc`). So the page-math bugs on this page (duplicates, missing items, the last page) apply to all three patterns. For search results specifically, see [Search, filters & sorting](/features/search-filters-and-sorting).
</Callout>

## Designs & variants

- **Full pager (web, desktop):** ‹ 1 … 4 **5** 6 … 16 ›. Shows first, last, the current page and its neighbors, with an ellipsis for the gaps.
- **Compact pager (phones):** ‹ Prev · Page 5 of 16 · Next ›. Fewer, bigger targets. Material and Apple's guidelines don't define a numbered pager; mobile apps usually prefer "Load more" or infinite scroll.
- **Prev / Next only:** for feeds or cursor-based APIs where the total isn't known.
- **With a page size selector:** "Per page: 20 / 50 / 100", common in tables and admin tools.
- **With a result summary:** "Showing 81–100 of 312". Small text, many bugs.

## When to use it

- Users need to **find, compare and come back to** items: shops, search results, statements, admin tables.
- The list is **long** (hundreds or thousands of items) and loading everything would be slow.
- The page should be **shareable or bookmarkable** ("look at page 3 of the sale").
- There is important content **below the list**: a footer, filters, contact details.

## How good pagination behaves

### The page lives in the URL

On the web, the current page (and page size, sort, filters) belongs in the address: a <Term id="query-parameter" /> like `shop.example.com/products?page=3&size=20`. That single decision makes **Back**, **Refresh**, **bookmarks** and **shared links** all work. If the URL never changes, Back from a product takes the user to page 1, and a refresh throws away their place.

In apps, the same idea applies: after opening an item and going back, the list must be **exactly where it was**: same page, same loaded items, same scroll position.

### The math is right at every boundary

Page *n* shows items `(n − 1) × size + 1` to `n × size`, but **never more than the total**. Classic <Term id="boundary-value-analysis" /> applies; test these pages every time:

| Page | What should happen |
| --- | --- |
| **1** | Prev disabled. Items 1–20. |
| **2** | Starts with item 21. Nothing from page 1 repeats. |
| **Last (16)** | Next disabled. "Showing 301–312 of 312". Only 12 items. |
| **0, −1, abc** | Redirect to page 1 (or a clear error). Never a crash. |
| **999** | A helpful "This page doesn't exist" with a link to the last page. Not an endless spinner. |

<Callout type="bug" title="The off-by-one">
If page 2 starts with the **last item of page 1**, someone wrote `offset = (page − 1) × size − 1`. If an item is **skipped**, the offset is one too big. Both are <Term id="off-by-one-error">off-by-one errors</Term>. To spot them, always compare the **last item of one page** with the **first item of the next**.
</Callout>

Also check the edges of the data, not just of the pager: **0 results** (an empty state, no pager), **exactly one page** (no pager, or both arrows disabled), **exactly 20 items with 20 per page** (one page, not two with an empty second one), and a **last page with exactly one item**.

### Changing the page size lands somewhere sensible

On page 8 with 20 per page, the user switches to 50 per page. There are now only 7 pages, so "page 8" doesn't exist. Good apps go back to page 1, or better, to the page that contains the item the user was looking at (item 141 → page 3). Same rule when a **filter** reduces the results: never leave the user on a page that no longer exists.

### Data that changes between pages

Lists aren't frozen. While you read page 1, new listings get posted and others sell out. With **offset** pagination ("skip 20, take 20"), that shifts everything: you see **duplicates** when items are added, and **miss items** when items are removed. **Cursor** pagination ("20 items after item X") largely avoids it, because each page starts right after the last item you actually received. ## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Off-by-one offset** | Last item of page 1 repeats on page 2, or one item is never shown | High |
| 2 | **Wrong result summary** | "Showing 301–320 of 312" on the last page | Low |
| 3 | **Next enabled on the last page** | Leads to an empty page or an error | Medium |
| 4 | **Out-of-range page** | `?page=999` shows an endless spinner, a crash or a blank page | Medium |
| 5 | **Page size change keeps the page** | Page 8 of 7: an empty list | Medium |
| 6 | **Page not in the URL** | Back, refresh or a shared link always open page 1 | Medium–High |
| 7 | **Duplicates or gaps after data changes** | The same item twice, or items missing across pages | Medium |
| 8 | **Wrong total** | "16 pages" but page 16 is empty, or the count ignores a filter | Medium |
| 9 | **Tiny targets on phones** | 24 px page numbers, users hit 4 instead of 5 | Medium |
| 10 | **Filters/sort reset when paging** | Page 2 shows unsorted, unfiltered results | High |

### Tools

- **The URL bar** is your best tool: edit `?page=` and `?size=` by hand to hit every boundary in seconds.
- **DevTools › Network** (see [DevTools for testers](/web/devtools-for-testers)): filter by the API path and check `page`, `offset`, `limit` or `cursor` for each click. An `offset=19` on page 2 is a bug you can prove.
- **API directly** ([Postman](/web/api-testing-with-postman)): request the last page, `page=0`, a negative page and a huge page; check status codes and the `total` field.
- **Mobile apps:** use a [proxy tool](/mobile/proxy-tools) (Charles, Proxyman) to see the paging requests behind "Load more" and infinite scroll.

## Accessibility

- **Landmark.** The pager is a navigation landmark, so <Term id="screen-reader" /> users can jump straight to it. If there are two pagers (top and bottom), label them differently or keep only one.
  <DevNote>Wrap the pager in `<nav aria-label="Pagination">`.</DevNote>
- **Current page.** Mark it with a visual style that isn't only color (bold, filled background). Screen readers then say "Page 3, current page".
  <DevNote>Mark it with `aria-current="page"`.</DevNote>
- **Real links or buttons.** Page numbers should be links or buttons. Give arrow-only controls an accessible name: "Previous page", "Next page". Hide the ellipsis from screen readers.
  <DevNote>Links like `<a href="?page=3">`, not clickable `<span>`s.</DevNote>
- **Disabled states.** Prev on page 1 and Next on the last page should be disabled *and* announced as dimmed or unavailable, not just greyed out with a working click.
- **<Term id="keyboard-navigation">Keyboard</Term>.** Everything reachable with <kbd>Tab</kbd>, visible focus, <kbd>Enter</kbd> activates. After changing page, move focus to the top of the results (or the results heading) so keyboard users don't have to tab back up through the whole page.
- **<Term id="touch-target">Touch targets</Term>.** At least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px, and 44×44 px (2.5.5, AAA) is the comfortable target. A row of ten 24 px numbers is a classic mobile failure; a compact "Page 3 of 16" with big Prev/Next buttons is better.
- **Infinite scroll** is hard for keyboard and screen reader users: new items appear without notice and the footer is unreachable. Offer a "Load more" button or a way to pause loading.

## Mobile vs web

<Tab>

- No native numbered pager. Lists usually load the next page when the user nears the end (infinite scroll) or show a **Load more** row.
  <DevNote>`UITableView`, SwiftUI `List`.</DevNote>
- Test on a slow network: is there a loading row at the bottom? What happens if loading fails: a **Retry** button, or a silent dead end?
- Pull to refresh while on "page 3" of loaded items: does the list reset cleanly without duplicates?
- Open an item, go back: the list must keep every loaded item and the scroll position.

<Tab>

- Lists usually load pages as you scroll.
  <DevNote>`RecyclerView` with the Paging library, or a `LazyColumn` in Compose.</DevNote>
- Check **rotation** and **process death** (Developer options › *Don't keep activities*): does the list come back on the same position, or restart from the top?
- Fast scrolling ("fling") through hundreds of items: watch for duplicates, gaps, placeholders that never fill and jumps in position.
- Use **airplane mode** mid-scroll: a clear error row with Retry, not an endless spinner.

</Tab>
<Tab>

- Numbered pagination is most common here. The page must be in the **URL**: test Back, Forward, Refresh, bookmarks and shared links.
- Edit the URL by hand: `?page=0`, `?page=999`, `?page=abc`, `?size=10000` (does the server cap the size?).
- Check the **responsive** layout: at 360 px, does the pager wrap neatly, switch to a compact version, or overflow the page?

<KeyTakeaways>

- Pagination is **math, state and boundaries**. Always compare the last item of one page with the first of the next.
- Test **page 1, page 2, the last page, page 0, page 999** and invalid values like `abc`.
- The page belongs in the **URL** so Back, refresh and shared links work. In apps, the list must keep its place after going back.
- Changing the **page size, sort or filters** must never leave the user on a page that doesn't exist.
- Data that changes between page loads causes **duplicates and gaps** with offset paging.
- Choose the pattern on purpose: **numbered pages** to find and return, **Load more** for mobile lists, **infinite scroll** for feeds only.
- Accessibility: a **nav landmark**, `aria-current="page"`, real links or buttons, and **44 pt / 48 dp** touch targets.

</KeyTakeaways>
