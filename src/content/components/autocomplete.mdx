Type "Lon" in a travel app and London Heathrow appears. Type the first letters of your street at checkout and the full address is offered. Type "@gm" in an email field and "gmail.com" is filled in. That's <Term id="autocomplete" />: a text field that **guesses what you mean** while you type.

It feels simple, but it's a [text field](/components/text-field), a [dropdown](/components/dropdown) and a small search engine glued together, with a network request on every pause. Bugs hide in the glue: what's typed vs what's selected, which response arrives last, which keys do what. This page is about the **autocomplete field**. The search results page behind a [search bar](/components/search-bar) and the timing of search requests in general are covered in [Search, filters & sorting](/features/search-filters-and-sorting).

## What is autocomplete?

An autocomplete field is a **text input that shows matching suggestions as you type, so you can pick one instead of typing it all**. In code (on the web and in accessibility specs) it's called a **combobox**: a combination of an editable box and a list of options.

There are two important questions for every autocomplete, and testers should know the answer before starting:

- **Must the user pick from the list, or is free text allowed?** A city for delivery, an airport, a country or a product variant must be **one of the options** (it has an id behind it). A search query, a tag or a town that might not be in the list can be **anything**.
- **Where do suggestions come from?** A **local** list (200 countries, built into the app) is instant. A **server** search (millions of addresses) is slow, can fail, and answers in an unpredictable order.

### List, inline, or both

| Style | What happens | Typical use |
| --- | --- | --- |
| **List** | A list of matching options opens under the field | Cities, addresses, products, people |
| **Inline** | The rest of the word is filled in and selected; typing on replaces it | Browser address bar, email domains |
| **List + inline** | The list opens and the first match is also completed in the field | Some address bars and code editors |

<DevNote>In ARIA terms these are `aria-autocomplete="list"`, `"inline"` and `"both"`. You'll see these values in <Term id="devtools" /> when you inspect the field.</DevNote>

### How it differs from similar components

| Component | You type… | You get… |
| --- | --- | --- |
| **Autocomplete / combo box** | Part of a name | Suggestions; one becomes the value (or free text) |
| **[Dropdown / select](/components/dropdown)** | Nothing (or one letter to jump) | One option from a fixed list |
| **[Search bar](/components/search-bar)** | A query | A results page; suggestions are only shortcuts |
| **[Chips](/components/chips) / token field** | Part of a name, many times | Several selected values shown as chips |
| **Browser autofill** | Nothing | Saved personal data filled into a form (see [Text field](/components/text-field)) |

<Callout type="info" title="Same word, different things">
"Autocomplete" also names the HTML attribute `autocomplete="email"`, which controls **browser autofill**, not suggestions from the app. Many teams use "autocomplete", "typeahead" and "combo box" for the same component. In bug reports, say exactly which field and which list you mean.
</Callout>

### How a good autocomplete behaves

**It waits for enough input.** One letter matches half the list and wastes a server call. Most fields start after 2–3 characters (local lists can start at 1) and say so: "Type at least 2 letters".

**It waits for a pause, and ignores old answers.** Requests are sent after a short <Term id="debounce" /> (around 200–300 ms). Responses can arrive in any order, so the app must only show the answer to the **latest** query. Otherwise the slow answer for "no" overwrites the fast answer for "novi": a <Term id="race-condition" />. The [Search, filters & sorting](/features/search-filters-and-sorting) page shows this with a live demo.

**It matches the way people type.** Case and accents are ignored (<Term id="diacritics" />: "sabac" finds Šabac), and words in the middle count ("sad" finds Novi Sad). The [Dropdown](/components/dropdown) page has a matching lab for this.

**It highlights the matched part,** using the **same** matching rules. If the search ignores accents but the highlighting doesn't, users see options with nothing bold and wonder why they're there.

**It shows the empty and the loading state.** "No cities match 'nobi'. Check the spelling." is an <Term id="empty-state" />; a spinner or "Searching…" covers slow networks. Silence (no list at all) looks like a broken field.

**It keeps typed text and selected value apart.** The text in the field is just text until the user **chooses** an option. If they edit the text afterwards, the selection must be cleared. And if they leave the field without choosing, a must-pick field shows an error (or accepts an exact match), but never saves "novi" as a city.

**It obeys the keyboard.** Arrows move through the options, Enter chooses, Esc closes the list (a second Esc may clear the field), Tab moves on. More in [Accessibility](#accessibility).

**It closes when it should:** after choosing, on Esc, when focus leaves the field, and when the user taps outside.

<Callout type="tip" title="Ask early: what is the value?">
Before testing, find out what the form actually **sends**: the text, or an id (city id, place id, airport code)? Then test every way to leave the field (Tab, tap outside, Enter, Back, submit) and check the request in the network tab. Most serious autocomplete bugs are a mismatch between what the user **sees** and what the form **saves**.
</Callout>

## When to use it

Autocomplete is a good choice when:

- The list is **long** (cities, airports, addresses, medicines, products), too long to scroll in a [dropdown](/components/dropdown).
- Users **know what they want** and can type the first letters.
- **Typing it fully is error-prone**: long names, accents, exact spellings needed for delivery.
- You want to **suggest** but still allow free text (search queries, tags, small towns).

## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Typed text saved, nothing chosen** | "novi" is saved as the city; no postcode, no id | High |
| 2 | **Stale results** | The list shows results for an older query | Medium–High |
| 3 | **No keyboard support** | Arrows do nothing; Enter submits the form | High (for affected users) |
| 4 | **Esc clears the field** | Instead of closing the list, Esc wipes what you typed | Medium |
| 5 | **List won't close** | It stays open after Tab or a tap outside and covers the form | Medium |
| 6 | **Edited after choosing** | Change "Novi Sad" to "Novi Pazar" by typing: the old id is still sent | High |
| 7 | **Accents and case** | "sabac" finds nothing, or finds Šabac but highlights nothing | Medium |
| 8 | **No empty or loading state** | Nothing appears, so users think the field is broken | Medium |
| 9 | **Request on every keystroke** | Ten requests for ten letters; flicker and rate limits | Medium |
| 10 | **Hidden by the keyboard** | On a phone, the list opens behind the on-screen keyboard | High |
| 11 | **Silent for screen readers** | No result count, options not announced | High (for affected users) |
| 12 | **Special characters** | `&`, `'` or `%` break the request ("O'Hare", "Ivo & Co") | Medium |

<Callout type="bug" title="Why #1 and #6 are so sneaky">
On screen everything looks right: the field says "novi" or "Novi Pazar". The problem is in the **data** behind it, which the screen doesn't show. Always check the request with <Term id="devtools" /> or a [proxy tool](/mobile/proxy-tools), or check the saved record afterwards (order details, confirmation email). Ask: does the saved id belong to the text the user sees?
</Callout>

## Accessibility

Autocomplete is one of the hardest components to make accessible, and custom ones often fail. Check these (the <Term id="aria" /> combobox pattern):

| Key | What it should do |
| --- | --- |
| <kbd>↓</kbd> / <kbd>↑</kbd> | Open the list / move the active option |
| <kbd>Enter</kbd> | Choose the active option and close the list |
| <kbd>Esc</kbd> | Close the list (keep the text); a second Esc may clear |
| <kbd>Tab</kbd> | Leave the field (and close the list) |

- **The active option** is announced: focus stays in the input (so typing still works) while the screen reader reads "Novi Pazar, 2 of 4".
  <DevNote title="Roles and states">The input has `role="combobox"`, `aria-expanded`, `aria-controls` (pointing to the list) and `aria-autocomplete`. The list has `role="listbox"`, each option `role="option"`. The active option is announced via `aria-activedescendant`.</DevNote>
- **Result count:** a polite live region says "4 results available" or "No results" after typing stops. Without it, <Term id="screen-reader" /> users don't know a list appeared.
- **Visible focus** on the field and a clear style for the active option, different from hover. Text 4.5:1, the active-option background and field border 3:1 (WCAG 1.4.3 / 1.4.11).
- **<Term id="touch-target">Touch targets</Term>:** options at least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px; 44×44 px (2.5.5, AAA) is the comfortable target.
- **No surprise changes:** suggestions must not move focus or submit the form on their own (WCAG 3.2.2 On Input, Level A).
- **Zoom and small screens:** at 200 % zoom and 320 px width, the list fits and scrolls (WCAG 1.4.10 Reflow, Level AA).

Read more in [Accessibility basics](/web/accessibility-basics).

## Mobile vs web

<Tabs labels={['iOS', 'Android', 'Web']}>
<Tab>

- There's **no standard autocomplete control** on iOS.
  <DevNote>Not in UIKit. Apps build one from a text field and a table, or use SwiftUI's `.searchable` with `.searchSuggestions`.</DevNote>
- Test address suggestions with real addresses in different countries.
  <DevNote>Address suggestions often come from MapKit's `MKLocalSearchCompleter` or a third-party places API.</DevNote>
- The **keyboard covers half the screen**: lists usually open full screen or right below a field moved to the top. Check on the smallest iPhone you support.
- **Autocorrect** can change what users type ("Nis" → "Mis"). Address and city fields usually turn it off.
- Test **VoiceOver** (is the number of results announced?) and **Dynamic Type** (do long names wrap or truncate?).

</Tab>
<Tab>

<DevNote>Views: `AutoCompleteTextView` / `MaterialAutoCompleteTextView`, often inside a `TextInputLayout` (Material **exposed dropdown menu**). Compose: an editable `ExposedDropdownMenuBox`.</DevNote>

- The popup can open **above** the field when there's no room below. Test near the bottom of the screen with the keyboard open.
- **Back** should close the suggestions first, then the keyboard, then the screen.
- Test **TalkBack**, **font scale**, **landscape** (very little room above the keyboard) and a **slow network**.

</Tab>
<Tab>

<DevNote>Native: `<input list="…">` with a `<datalist>`. It allows free text, needs no JavaScript, but looks and behaves differently in each browser and offers little control over matching.</DevNote>

- Custom components (React, Vue, UI libraries) must follow the ARIA combobox pattern; check roles and `aria-activedescendant` in <Term id="devtools" /> (Elements and Accessibility panes).
- Check the **Network** tab for debouncing and the order of responses; use the "Slow 4G" and "3G" presets.
- Browser **autofill** can pop up on top of the app's own suggestions; check that the two never overlap.
  <DevNote>Teams often set `autocomplete="off"` on the combobox for that reason.</DevNote>
- Test in Chrome, Safari and Firefox, with **zoom**, and at narrow widths.

</Tab>

<KeyTakeaways>

- An autocomplete is a **combobox**: a text field plus a list of suggestions. Know whether it's **must-pick** or **free text** before testing.
- The text in the field is **not** the value until the user chooses. Check what the form **sends**, especially after editing, Tab, Esc and Back.
- **Debounce** and **ignore stale responses**; test by typing fast on a slow network.
- Matching and **highlighting** must ignore case and accents the **same way**.
- Keyboard: **arrows, Enter, Esc (close, keep text), Tab**; the list closes on blur and outside taps; screen readers hear the **result count**.
- On phones, make sure the list isn't **hidden by the keyboard**.

</KeyTakeaways>
