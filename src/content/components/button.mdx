You tap **Place order** in a food delivery app. Nothing seems to happen, so you tap again. Ten minutes later two pizzas arrive and your card was charged twice. That's a <Term id="button">button</Term> bug, and it's one of the most expensive bugs a team can ship.

Buttons look like the simplest thing on the screen. But every button has several **states**, talks to a **server**, and has to work with **touch, mouse, keyboard and screen readers**. That's a lot of places for bugs to hide.

## What is a button?

A button is a control that **starts an action when you tap or click it**: pay, send, save, delete, add to basket. The label tells you what will happen, and the look tells you how important the action is.

You'll see buttons used to:

- **Commit an action**: *Place order*, *Send money*, *Book flight*.
- **Move forward in a flow**: *Continue*, *Next*, *Sign up*.
- **Do something small in place**: *Like*, *Share*, *Add another item*.
- **Destroy something**: *Delete account*, *Remove card*, *Cancel subscription*.

### How it differs from similar components

A common finding is a button that should have been something else, or something else pretending to be a button.

| Component | What happens on tap | Keeps a state? | Typical use |
| --- | --- | --- | --- |
| **Button** | Runs an action | No (it doesn't stay "on") | Pay, Save, Send, Delete |
| **Link** | Navigates to another page or screen | No | "View order details", "Terms of service" |
| **Toggle switch** | Turns a setting on or off immediately | Yes, on/off | Notifications, Wi-Fi |
| **Segmented control** | Picks one of a few views | Yes, one selected | List / Map |
| **Chip** | Filters or adds a tag | Often | "Vegan", "Under €20" |
| **Menu item** | Runs an action from a list | No | Overflow menu: Rename, Duplicate |

<Callout type="info" title="Button or link?">
A simple rule: **if it does something, it's a button. If it goes somewhere, it's a link.** On the web this really matters: links open in a new tab with Ctrl/Cmd-click and show their URL, buttons submit forms and react to the Space key. A "button" built from a `div` or a link that runs JavaScript breaks keyboard and screen reader users.
</Callout>

## Designs & variants

Buttons come in **emphasis levels**. The more important the action, the louder the button. Each platform has its own names for them.

<VariantsGallery client:visible />

| Emphasis | iOS | Android (Material 3) | Web (typical) | Use it for |
| --- | --- | --- | --- | --- |
| **High** | Filled (`.borderedProminent`) | Filled | Primary | The main action. One per screen. |
| **Medium** | Tinted / Gray (`.bordered`) | Filled tonal, Outlined | Secondary | Alternatives: Save for later, Cancel |
| **Low** | Plain (`.borderless`) | Text | Tertiary, link-style | Skip, Learn more, Forgot password? |
| **Destructive** | `role: .destructive` (red) | Error color (custom) | Danger | Delete, Remove, Cancel subscription |
| **Floating** | Not used | FAB, extended FAB | Rare | The screen's main creation action |

<Callout type="tip" title="The loading state is a promise">
When a button shows a spinner, it promises two things: **"I heard you, don't tap again"** and **"I will finish"**. A spinner that still accepts taps causes <Term id="double-submit">double submits</Term>. A spinner that never stops after an error leaves the user stuck. Always test the <Term id="loading-state">loading state</Term> with a slow network *and* with a failing one.
</Callout>

## When to use it

A button is the right choice when:

- Tapping it **performs an action** (saves, sends, pays, deletes) rather than just showing another page.
- The action has a clear **verb** you can put on the label.
- There is a clear **hierarchy**: one primary action, maybe a secondary one, and the rest as low-emphasis buttons.
- The action needs **feedback**: a loading state, a success message or an error.

<Callout type="tip" title="Writing good labels">
Labels should start with a **verb** and name the **thing**: *Save changes*, *Add to basket*, *Send €50 to Anna*. Avoid *OK*, *Yes*, *Submit* and *Click here*. Check the label still fits in German and at the largest text size, and that it matches the action (a button labeled *Save* that also sends an email is a bug).
</Callout>

## Common bugs

These are the button bugs testers report again and again. Many of them cost real money.

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Double submit** | Two quick taps create two orders, two payments or two messages | Critical |
| 2 | **Endless spinner** | After a network error the button keeps loading forever, with no message and no retry | High |
| 3 | **Disabled button still works** | A greyed-out button can still be tapped, clicked or triggered with Enter | High |
| 4 | **Never enabled** | The button stays disabled even after the form is valid, often after autofill or paste | High |
| 5 | **Label truncated** | "Place ord…" or the price cut off in other languages or with large text | Medium |
| 6 | **Hidden CTA** | The sticky button sits under the keyboard, the home indicator or a cookie banner | High |
| 7 | **No confirmation for destructive actions** | "Delete account" or "Clear basket" happens instantly with no confirm or undo | High |
| 8 | **Tap area too small** | Only the icon reacts, not the whole visible button. Users miss it | Medium |
| 9 | **No pressed or focus feedback** | Nothing changes on tap, or keyboard users can't see which button is focused | Medium |
| 10 | **Layout jump on loading** | The button shrinks to the spinner's size, so the layout jumps and the next tap lands on something else | Low–Medium |

<Callout type="bug" title="Why double submits happen">
The app sends a request on every tap and only disables the button when the response comes back. On a fast office Wi-Fi the gap is a few milliseconds, so developers never see it. On a train with a weak signal, the gap is seconds. The fix is twofold: the app **blocks repeat taps** while loading, and the server uses <Term id="idempotency" /> keys so the same order can never be created twice.
</Callout>

## Accessibility

Buttons are where many users first get stuck. Check these:

- **Role and name:** <Term id="screen-reader">Screen readers</Term> must announce the label and the word "button". A clickable `div` has no role, can't be focused with Tab, and ignores Enter and Space.
  <DevNote>On the web, use a real `<button>` element.</DevNote>
- **Icon-only buttons** need an accessible name.
  <DevNote>`accessibilityLabel` on iOS, `contentDescription` on Android, `aria-label` on the web.</DevNote>
- **Disabled and busy states** must be announced: "dimmed" on iOS, "disabled" on Android and the web. While loading, a live message ("Processing payment") tells the user something is happening.
  <DevNote>Or `aria-busy="true"`.</DevNote>
- **<Term id="touch-target">Touch targets</Term>:** at least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.2 asks for at least 24×24 CSS px (2.5.8, level AA); 44×44 CSS px (2.5.5, level AAA) is the comfortable target.
- **Contrast:** label text at least **4.5:1** against the button, and the button's shape at least **3:1** against the background. Disabled buttons are exempt, but they must still be recognizable.
- **Focus:** on the web, every button is reachable with <kbd>Tab</kbd>, has a visible focus ring, and works with both <kbd>Enter</kbd> and <kbd>Space</kbd>.
- **Don't rely on color alone** for destructive actions. Red plus a clear label ("Delete account") works for color-blind users too.

## Mobile vs web

<Tabs labels={['iOS', 'Android', 'Web']}>
<Tab>

<DevNote>Native: `UIButton` with `UIButton.Configuration` (filled, tinted, gray, plain) or SwiftUI `Button` with `.borderedProminent`, `.bordered`, `.borderless`.</DevNote>

- Pressed state is a quick **dim/highlight**, not a ripple.
- Destructive actions are red, often inside an **action sheet** or alert.
  <DevNote>They use `role: .destructive`.</DevNote>
- No FAB: the main action usually lives in the navigation bar or a bottom toolbar.
- Test with **Dynamic Type**, VoiceOver, and on small screens like iPhone SE where sticky buttons get tight.

</Tab>
<Tab>

- Material 3 buttons: **filled, filled tonal, outlined, text, elevated**, plus **icon buttons** and the **FAB**.
- Pressed state shows a **ripple** and a state layer. Disabled = 38% opacity content on a 12% container.
- Watch for the **system back gesture** during loading: does going back cancel the request or leave a ghost order?
- Device <Term id="fragmentation" /> matters: test small and large screens, font scale, display size and TalkBack.
- Developer options › **Show layout bounds** reveals the real tap areas.

</Tab>
<Tab>

- Use `<button>` for actions and `<a href>` for navigation. Inspect the element in <Term id="devtools">DevTools</Term> to check.
- A button inside a form submits it by default, which causes surprise submits.
  <DevNote>`type="submit"` vs `type="button"` matters.</DevNote>
- Test **hover, focus and active** styles, and pressing <kbd>Enter</kbd> in a text field (does it submit twice?).
- Check the button on mobile browsers too: sticky bars vs the browser's own toolbar and the on-screen keyboard.
- Use DevTools network throttling to test the loading state and double clicks.

</Tab>
</Tabs>

<KeyTakeaways>

- A button **does something**; a link **goes somewhere**. Pick the right one, and use one primary button per screen.
- Every button has **six states**: default, hover, pressed, focused, disabled and loading. Test all of them, in light and dark mode.
- The costliest bugs are **double submits**, **endless spinners** and **disabled buttons that still work**. Test with slow and failing networks.
- Labels should be **specific verbs** that fit at every text size and in every language.
- Check **touch targets** (44 pt / 48 dp), **confirmation for destructive actions**, and **screen reader** announcements.

</KeyTakeaways>
