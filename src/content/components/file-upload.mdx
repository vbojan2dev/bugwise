You attach a scanned invoice to an expense claim, upload a signed rental contract, send a CSV of transactions to your accountant, add your CV to a job application. Then you press **Submit** and trust that every file arrived, complete and readable.

Sometimes it didn't. The scanner saved the file as `SCAN_0042.PDF` and the app said "file type not supported". The hotel invoice uploaded for two minutes before the app mentioned a 10 MB limit. One of three receipts failed on the train and quietly vanished from the list. File upload looks like one button, but it's a small system of its own, and testers who know what to feed it find bugs every time.

## What is a file upload?

A file upload component lets the user **choose one or more files from their device and send them to a server**. It usually has three jobs:

1. **Picking**: a button that opens the system file picker, and on the web often a drop zone for drag and drop.
2. **Checking**: is the type allowed, is it under the size limit, are there too many files?
3. **Uploading**: sending each file, showing its progress, and handling cancel, failure and retry.

You'll find it in expense apps (receipts), banking and insurance (statements, claims), job portals (CV), email and chat (attachments), cloud storage, and admin tools (CSV imports).

### The states of one file

Every file in the list goes through its own life cycle, and the whole component is only "done" when **all** files are. A good list shows each file's state separately:

| State | What the user sees | What to check |
| --- | --- | --- |
| **Rejected** | "Not added" with the reason | The reason is specific: type, size, count, empty file |
| **Uploading** | Progress bar, percentage, **Cancel** | The bar moves; Cancel really stops the request |
| **Processing** | Bar full, "Processing…" | The app doesn't look frozen at 100% |
| **Uploaded** | Check mark, **Remove** | The server has the right file, complete and openable |
| **Failed** | Error text, **Retry**, **Remove** | The file stays in the list; Retry works |
| **Canceled** | "Canceled", **Retry** or gone | Matches the spec; nothing half-uploaded is kept |

The same idea appears as a plain browser input, a drop zone, a single "Upload CV" field, a paperclip in a chat, or the system document picker on a phone.

### The native file input

On the web, everything starts with `<input type="file">`. Two attributes matter most for testers:

- **`accept`** (for example `accept=".pdf,.docx"` or `accept="application/pdf"`) filters what the picker shows. It's a **hint, not a check**: desktop dialogs offer an "All files" option, and files dropped onto a drop zone ignore `accept` completely.
- **`multiple`** allows picking several files at once. Without it, the second file **replaces** the first, which surprises users who expected to add more.

Custom-designed upload buttons usually hide the real input and trigger it from a styled button. That's fine, as long as the visible control is a real, focusable button.

### Drag and drop is a shortcut, not the way in

A drop zone is great on a desktop with a file explorer open. It's useless on a phone, for keyboard users, for many screen reader users and for anyone who finds dragging hard. Drag and drop must always come **with** a Browse button that does the same thing. Testers also check what happens when a file is dropped **outside** the zone: the browser shouldn't simply open the PDF and leave the page (with the user's half-filled form).

### Mobile document pickers

Phones don't let apps browse the whole file system. Instead, the app asks the **system picker**, the user chooses, and the app gets access to just those files. No storage <Term id="app-permissions">permission</Term> is needed for this.

| | iOS | Android |
| --- | --- | --- |
| **Picker** | Document picker (the Files app UI: Recents, Shared, Browse) | Storage Access Framework picker ("Open from", Recent, Downloads, Drive) |
| **Sources** | On My iPhone, iCloud Drive and installed providers like Google Drive or Dropbox | Device storage, Downloads, and providers like Google Drive |
| **Multiple** | Only if the app enables it | Only if the app requests it |
| **Typical traps** | Cloud files not downloaded yet, file names with emoji, files from other apps that disappear later | Files without a real name or size, Drive files that need a download first, older OS versions |

On a mobile **website**, the same `<input type="file">` opens a system menu instead of a desktop dialog (on iPhone: Photo Library, Take Photo or Video, Choose File). The `accept` list changes which options appear, so test on real phones, not only in a desktop browser.

A few things to try, and what they teach:

- **Extension, exact case** rejects `SCAN_0042.PDF`. Users don't care about letter case, and many scanners and older systems write uppercase extensions.
- **MIME type (File.type)** looks smarter, but the browser usually guesses the type **from the extension**. `holiday-photo.pdf` (a PNG renamed to .pdf) still passes. Only the server, looking at the actual bytes, can catch it.
- **Client-side checks off** shows why the app should check early: the 48 MB ZIP uploads completely before the server says no. The server still protects itself, but the user wasted time and mobile data.
- **Unstable** network: failed files stay in the list with **Retry**. Nothing silently disappears.

<Callout type="warning" title="Client checks are convenience, the server is the gatekeeper">
Every check in the app or browser (`accept`, extension, size, count) can be skipped by a curious user with <Term id="devtools" /> or a <Term id="proxy-tool" />. The server must check again: the **real content** (by its first bytes, the "magic number"), the size, the count, and that the user is allowed to upload there at all. In a test environment, try a text file renamed to `.pdf`, a file over the limit sent directly to the API, and a file with a double extension like `invoice.pdf.exe`. Expect a clear rejection (often HTTP **413** for too large, **415** for the wrong type). More in [Security basics](/web/security-basics).
</Callout>

### File names are test data

The name is the part of a file that developers forget most. Keep these in your <Term id="test-data">test kit</Term>:

| Name | What can go wrong |
| --- | --- |
| `SCAN_0042.PDF` | Uppercase extension rejected |
| `Lease agreement (signed) final.docx` | Spaces and brackets break links or downloads |
| A 120-character name | Overflows the row, pushes the Remove button off-screen, or is cut by the server |
| `Mietvertrag_endgültig.pdf`, `Résumé.pdf`, `报告.pdf`, `🧾.pdf` | <Term id="diacritics" />, other scripts and emoji turn into `???` or `Ã¼` |
| `invoice.pdf.exe`, `report.` and a name without any extension | Wrong type detected, or the app crashes on a missing extension |
| `Invoice_March.pdf` twice (from two folders) | Duplicate, or the second silently **overwrites** the first on the server |

<Callout type="tip" title="Middle truncation keeps the extension">
When a name is too long, cut it in the **middle**: `Hotel_invoice_Grand_Ho…_884213.pdf`. The user still sees how it starts **and** what type it is. Cutting at the end hides the extension, and not cutting at all breaks the layout. See <Term id="truncation" />.
</Callout>

## When to use it

- The user has to provide a **document that already exists** on their device or in the cloud: receipts, contracts, statements, CVs.
- The content is too big or too structured to type: a CSV import, a ZIP of project files.
- Several files belong together and should be checked and submitted as **one set** (an insurance claim with photos, invoices and a police report).

## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Browse not keyboard reachable** | The drop zone works with a mouse, but <kbd>Tab</kbd> never reaches a button | High (for affected users) |
| 2 | **Case-sensitive type check** | `SCAN_0042.PDF` or `.JPG` rejected | Medium–High |
| 3 | **Limits hidden** | Size or count limit shown only after a long upload fails | Medium |
| 4 | **Wrong file removed** | Tapping Remove on one file removes a different one | High (wrong documents submitted) |
| 5 | **Failure swallowed** | A failed file disappears, or the claim is sent without it | High |
| 6 | **Long names break the layout** | Name overflows, Remove button off-screen, text overlaps | Medium |
| 7 | **No progress or cancel** | Spinner forever, no way to stop a wrong 200 MB upload | Medium |
| 8 | **Duplicates** | Same file attached twice, or a second file with the same name overwrites the first | Medium |
| 9 | **Server trusts the client** | Renamed or oversized files are accepted when sent directly | High (security) |
| 10 | **Partial failure hidden** | "Upload complete" while 1 of 3 files failed | High |
| 11 | **Special characters mangled** | `Mietvertrag_endgültig.pdf` arrives as `Mietvertrag_endgÃ¼ltig.pdf` | Low–Medium |
| 12 | **Submit during upload** | **Submit** works while files are still uploading; the claim arrives without them | High |

<Callout type="bug" title="Partial failures are the sneaky ones">
With one file, failure is obvious. With five, the user sees four green ticks and assumes everything worked. The component must make the failed file impossible to miss (color **and** icon **and** text), keep it in the list with **Retry**, and either block Submit or clearly say "1 file was not uploaded". Test it on purpose with <Term id="network-throttling" /> or by switching the network off mid-upload ([Network conditions](/mobile/network-conditions)).
</Callout>

## Accessibility

- **A real, labelled button.** The control that opens the picker must be a real button with a clear name like "Browse files" or "Attach receipt". An icon-only paperclip needs an accessible name. Test <Term id="keyboard-navigation" />: <kbd>Tab</kbd> reaches it, <kbd>Enter</kbd> and <kbd>Space</kbd> open the picker (WCAG 2.1.1 Keyboard, Level A).
  <DevNote>A `<button>` (or a native file input).</DevNote>
- **Drag and drop is optional.** Everything must work without dragging. That's what keyboard, switch, <Term id="screen-reader" /> and most touch users rely on.
- **Rules are instructions.** Allowed types and limits are visible text near the control (WCAG 3.3.2 Labels or Instructions, Level A).
  <DevNote>The text is connected with `aria-describedby`.</DevNote>
- **Announce what happens.** "Invoice.pdf added", "uploaded" and "failed" should reach screen readers without moving focus, through a live region, per WCAG 4.1.3 Status Messages (Level AA). Errors are text, not only a red border (WCAG 3.3.1 Error Identification, Level A).
  <DevNote>`aria-live="polite"`, or `role="status"`.</DevNote>
- **Name every row action.** "Remove Invoice_March.pdf", "Retry Flight_LH1234.pdf", not five buttons called "×". Progress bars need a name and value.
  <DevNote>`role="progressbar"` with `aria-valuenow`, or a native `<progress>`.</DevNote>
- **Focus after actions.** After picking files, focus returns to the upload area. After removing a file, focus moves to a sensible place (the next row or the Browse button), not to the top of the page.
- **<Term id="touch-target">Touch targets</Term>:** Browse, Remove and Retry are at least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px; 44×44 px (2.5.5, AAA) is the comfortable target.
- **Not color alone.** Failed and uploaded states use an icon and text, not just red and green. Text needs 4.5:1 contrast, icons and borders 3:1 (WCAG 1.4.3 / 1.4.11).

- Apps open the **document picker**. Multiple selection and allowed types are set by the app; check both match the spec.
  <DevNote>UIKit `UIDocumentPickerViewController`, SwiftUI `fileImporter`.</DevNote>

<KeyTakeaways>

- File upload is three jobs: **picking**, **checking** and **uploading**. Each file has its own state: rejected, uploading, processing, uploaded, failed, canceled.
- **Drag and drop is a shortcut.** A real, labelled Browse button must do the same, for keyboard, screen reader and phone users.
- **Show the rules up front** (types, size, count) and reject bad files **before** uploading, with a specific message.
- Client checks are convenience. The **server** must check the real content, size and count. Type checks must ignore letter case.
- File names are test data: **long, unicode, spaces, uppercase extensions, the same name twice**.
- **Partial failures** must stay visible with Retry; Remove must remove exactly that file; Submit must not run ahead of uploads.
