Signing up for a food delivery app, searching for a flight, typing a card number, leaving a note for the courier: almost every journey in an app goes through a <Term id="text-field">text field</Term>. It's the most common input on the planet, and because users can type **anything** into it, it's also one of the richest places to find bugs.

In this lesson you'll learn what a good text field looks like on each platform, and how testers break the bad ones. For whole forms (validation timing, error summaries, server errors and real-world data), see [Forms and Validation](/features/forms-and-validation).

## What is a text field?

A text field is a **box that accepts free text from the keyboard**. It can be a single line (name, email, promo code) or several lines (a review, delivery instructions). Unlike a dropdown or a toggle, the user isn't choosing from options: they can enter any character, in any amount, in any language. That freedom is exactly what makes it risky.

You'll usually see text fields used for:

- **Personal data**: name, email, phone number, address.
- **Secrets**: passwords, PINs, one-time codes.
- **Search**: products, recipes, destinations.
- **Free-form content**: reviews, chat messages, notes for the courier.
- **Numbers that aren't really "numbers"**: postcode, card number, quantity, amount.

### How it differs from similar components

| Component | What the user does | Typical use |
| --- | --- | --- |
| **Text field** | Types a short, single line | Name, email, promo code |
| **Text area** (multiline field) | Types several lines | Reviews, messages, delivery notes |
| **[Search field](/components/search-bar)** | Types to find something, usually with instant results | Product search, filtering a list |
| **[Dropdown / select](/components/dropdown)** | Picks one value from a fixed list | Country, size, sort order |
| **Combo box** | Types to filter a list, then picks | Choosing a city from thousands |
| **[Date picker](/components/date-picker)** | Picks a date from a calendar or wheel | Birthday, booking dates |

<Callout type="dev" title="Platform names">
iOS calls it a **text field** (`UITextField`, or `TextField` in SwiftUI) and a **text view** for multiline. Android developers say **EditText**, while Material Design says **text field**. On the web it's an `<input>` element (or `<textarea>` for multiline). In bug reports, use the name your team uses.
</Callout>

## Designs & variants

Each platform has its own look. The parts are the same, but the risks differ: a floating label can overlap autofilled text, a left-hand label can truncate, a field with no visible label can confuse everyone.

### Types and mobile keyboards

On a phone, the field's **type** decides which keyboard appears. A missing or wrong type is a real, reportable bug: imagine typing an email on a keyboard with no `@` key, or a postcode on a full letter keyboard.

<KeyboardTypes client:visible />

<Callout type="warning" title="A keyboard is a hint, not validation">
A number pad doesn't guarantee numbers. Users can **paste** text, use a hardware or Bluetooth keyboard, or use autofill. Always test that a "numeric" field rejects or cleans `12abc`, even if the keyboard has no letters.
</Callout>

### States

A text field goes through several <Term id="ui-state">UI states</Term>. Each one needs to look different and behave correctly.

| State | What it looks like | What to check |
| --- | --- | --- |
| **Empty** | Label and maybe a placeholder | The placeholder is an example, not the only label |
| **Focused** | Highlighted border, cursor blinking, keyboard open | Focus is clearly visible (not only a color change) |
| **Filled** | Shows the value | Long values scroll or wrap; nothing is cut off on save |
| **Disabled** | Dimmed, can't be focused | Can't be edited by tapping, Tab key, or autofill. See <Term id="disabled-state" /> |
| **Read-only** | Looks like text, can be selected and copied | Can't be changed, but CAN be copied and read by screen readers |
| **Error** | Red border and a message | The message explains how to fix it, and disappears once fixed |
| **Loading** | Small spinner, e.g. "Checking username…" | Typing fast doesn't show the result for an old value |

<Callout type="tip" title="What testers check about validation">
Whatever strategy the team chose, check that it's **consistent** across the form, that the error **disappears as soon as the value is fixed**, and that the <Term id="error-message">error message</Term> says what to do ("Enter an email address like `name@example.com`"), not just what's wrong ("Invalid input").

### Autofill and autocomplete

Phones and browsers can fill in names, addresses, passwords and one-time codes for the user. It only works if each field tells the system what it contains.

| Field | Web `autocomplete` | iOS `textContentType` | Android `autofillHints` |
| --- | --- | --- | --- |
| Full name | `name` | `.name` | `personName` |
| Email | `email` | `.emailAddress` | `emailAddress` |
| Phone | `tel` | `.telephoneNumber` | `phone` |
| Street address | `street-address` | `.fullStreetAddress` | `postalAddress` |
| Postcode | `postal-code` | `.postalCode` | `postalCode` |
| New password | `new-password` | `.newPassword` | `newPassword` |
| SMS code | `one-time-code` | `.oneTimeCode` | `smsOTPCode` |

When testing autofill, check that values land in the **right fields** (no surname in the city field), that autofilled values pass **validation** (autofill sometimes adds a trailing space), and that floating labels don't **overlap** the filled text.

## When to use it

A text field is the right choice when:

- The answer is **truly open**: names, addresses, messages, search terms.
- There are **too many possible values** to list (every email address in the world).
- Users **know the answer** and typing is faster than scrolling (a postcode, a promo code).

## Common bugs

These are the text field bugs testers report again and again.

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Spaces break validation** | A valid email with a trailing space (from autofill or copy-paste) is rejected | High |
| 2 | **Error never clears** | You fix the value, but the red message stays until you submit again | Medium |
| 3 | **Silent truncation** | A phone number or address is cut off at a hidden limit, with no message | High |
| 4 | **Wrong character count** | The counter says "2/20" for one emoji, or a limit cuts an emoji in half | Low–Medium |
| 5 | **"Numeric" field accepts letters** | A postcode, quantity or year accepts `19ab` and saves it | Medium |
| 6 | **Wrong keyboard** | Email opens a keyboard with no `@`; a postcode opens letters | Medium |
| 7 | **Valid input rejected** | `O'Brien`, `Đurđa`, `anna+shop@test.com` or a 2-letter surname is refused | High |
| 8 | **Input rendered as HTML** | Typing `<b>Anna</b>` shows **Anna** in bold somewhere. A sign of an <Term id="xss">XSS</Term> hole | Critical |
| 9 | **Broken characters** | `Kovač` is saved or shown as `KovaÄ` or `Kova?` (an encoding bug) | Medium–High |
| 10 | **Paste blocked** | Paste does nothing in password or "confirm email" fields | Medium |
| 11 | **Data lost** | Text disappears after rotating, switching apps, or a failed submit | High |
| 12 | **Keyboard hides the field** | The field (or its error) is behind the on-screen keyboard and can't be seen | Medium |

<Callout type="bug" title="Why #8 is so serious">
If an app shows user input as HTML instead of plain text, an attacker can enter a tiny script instead of a name. Anyone who views that name (in a review, a chat, an admin panel) runs the attacker's script. Testers don't need to be hackers to spot the symptom: if **formatting tags take effect**, report it immediately.
</Callout>

## Accessibility

Text fields are where many users with disabilities get stuck. Check these:

- **A real label.** Every field needs a label connected to it in code. A placeholder doesn't count. Test it: tapping the label on the web should focus the field.
  <DevNote>`<label for>` on the web, `accessibilityLabel` on iOS, `labelFor` or a Material label on Android.</DevNote>
- **Screen readers** (<Term id="screen-reader">VoiceOver / TalkBack</Term>) should announce the label, the field type ("text field", "secure text field"), the current value, any hint and the error message.
  <DevNote>On the web, errors are linked with `aria-describedby` and marked with `aria-invalid="true"`.</DevNote>
- **Errors aren't color only.** A red border isn't enough: there must be text, ideally with an icon.
- **Contrast:** text, label and placeholder need at least 4.5:1 against the background; the field's border at least 3:1 (<Term id="wcag" />).
- **Big text:** at the largest <Term id="dynamic-type" /> sizes, labels and values must stay readable, not clipped.
- **<Term id="touch-target">Touch targets</Term>:** the field and its icon buttons (clear, show password) should be at least 44×44 pt on iOS and 48×48 dp on Android. On the web, WCAG 2.5.8 (AA) asks for at least 24×24 CSS px; 44×44 px (2.5.5, AAA) is the comfortable target.
- **Autocomplete attributes** help users with motor or memory difficulties fill forms without typing. On the web that's a WCAG requirement for fields about the user, too (1.3.5 Identify Input Purpose, Level AA).

- Floating labels: check they don't overlap autofilled text or the prefix/suffix.

<KeyTakeaways>

- A text field accepts **anything**, so test far beyond the happy path: empty, spaces, long, emoji, accented letters, apostrophes, HTML and pasted text.
- Every field needs a **visible label**. A placeholder is an example, not a label.
- The **input type** decides the mobile keyboard and autofill, but it's not validation.
- Errors should appear at a sensible time, **explain how to fix** the value, and **disappear once it's fixed**.
- The classic bugs: **untrimmed spaces, stale errors, silent truncation, wrong counts with emoji, wrong keyboards, valid names rejected, and input rendered as HTML**.

</KeyTakeaways>
