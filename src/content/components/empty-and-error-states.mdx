Designers spend weeks on the screen full of beautiful data. Then a real user signs up, opens **Orders** for the first time and sees… a white screen. Or a spinner that never stops. Or `Error 500`. The "nothing here" and "something broke" screens are often designed last, built in a hurry, and tested by nobody.

That makes them a gift for testers. Every list, feed, search and dashboard in an app has these states, and you can trigger most of them in a minute if you know how.

## What are empty and error states?

An <Term id="empty-state" /> is what a screen shows when it has **no content to display**. An **error state** is what it shows when it **couldn't get or show the content**. Together with the <Term id="loading-state" /> and the normal data state, they make up the <Term id="ui-state">UI states</Term> that every data screen must handle.

The key idea: **"empty" and "failed" are different situations** and need different messages. "You have no orders" and "We couldn't load your orders" might both show an empty list, but they mean opposite things to the user.

### The six types

<TypesGallery />

### Loading vs empty vs error

A screen that loads data goes through a few states. It should show **exactly one** at a time:

| State | What it means | What the user should see |
| --- | --- | --- |
| **Loading** | Request on its way | Skeleton or spinner, ideally in the same layout as the content |
| **Data** | Request OK, items returned | The content |
| **Empty** | Request OK, **zero** items | An empty state with a next step |
| **Error** | Request failed (offline, timeout, 500, 403) | An error state with a way to recover |

Most bugs on these screens are **mix-ups between these four**: an empty list treated as "still loading" (endless spinner), an error treated as "empty" (the user thinks their data is gone), or "empty" shown for a moment before the data arrives.

<Callout type="info" title="Where do toasts fit?">
A [toast](/components/toast) is for a **small, temporary** problem with an action the user just took ("Couldn't send. Retry"). When a **whole screen** can't load its content, the user needs an error state in the screen itself, because a toast disappears and leaves them looking at nothing. For how bad networks cause these states, see [Network conditions](/mobile/network-conditions).
</Callout>

Use a **full-screen** state when the screen's main content is missing (the whole list failed, no permission, offline with no cached data). Use **inline** messages for one section, one card or one form field, and a **banner** for ongoing conditions like "You're offline" while cached content stays visible.

### Wording: say it like a human

The words matter as much as the picture. A good <Term id="error-message" /> is **specific, calm and useful**:

<Compare>
<Do title="Plain, specific, actionable">

**We couldn't load your orders**
This is a problem on our side, not yours. Please try again in a moment.
**[Try again]**

</Do>
<Dont title="Codes, blame or dead ends">

**Error 500**
`TypeError: Cannot read properties of undefined (reading 'map')`
*Invalid request. You did something wrong.*

</Dont>
</Compare>

Rules to test against:

- **No raw codes or <Term id="stack-trace">stack traces</Term>.** "500", "-1009" or "TypeError" mean nothing to users and can leak technical details to attackers. A short reference ID for support ("Ref: 8F3K") is fine.
- **No blame.** "Invalid input" or "You did something wrong" for a server problem is both rude and false.
- **Say whose problem it is.** "Check your connection" (user can fix it) vs "This is on our side" (user should wait).
- **Always a next step.** Retry, Clear filters, Go to Home, Contact support. Never a dead end.
- **Don't lie.** An error shown as "No orders yet" makes users think their data is gone.

### Skeletons vs spinners

While data loads, a **skeleton** (grey shapes in the layout of the real content) feels faster and avoids layout jumps. A **spinner** is fine for short waits or small areas. Either way, test that the loading state **ends**: with data, with an empty state, or with an error. A loader that can spin forever is a bug.

## When to use it

Every screen that shows data needs an empty and an error state. Ask for them in reviews if the design only shows the "happy" screen. In particular:

- **Lists, feeds and grids**: orders, messages, favorites, notifications, search results.
- **Screens behind an account or role**: team data, admin pages, shared documents.
- **Anything that needs the network**: which is almost everything.
- **Features that need a permission**: camera, photos, location, contacts. If the user said no, explain why the feature needs it and how to turn it on in Settings.

## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Endless spinner** | Empty list or failed request, but the loader never stops | High |
| 2 | **Dead-end error** | "Something went wrong" with no Retry, no explanation, no way back | Medium–High |
| 3 | **Retry is broken** | Retry does nothing, or sends 2+ requests per tap (duplicate orders on POST!) | Medium–High |
| 4 | **Raw technical error** | `TypeError`, `500`, `null`, `undefined` or a stack trace on screen | Medium |
| 5 | **Empty flash** | "No orders yet" appears for a moment before the data loads | Low–Medium |
| 6 | **Error shown as empty** | Offline, 403 or 500 shows "No orders yet", so users think data was lost | High |
| 7 | **Wrong empty message** | Filtered list says "Place your first order" instead of "No results for this filter" | Low–Medium |
| 8 | **Stale error** | "You're offline" stays after reconnecting, or the error stays after a successful retry | Medium |
| 9 | **Two states at once** | Data and the empty message both visible, or spinner on top of an error | Low–Medium |
| 10 | **Silent for screen readers** | Error appears but VoiceOver / TalkBack says nothing; focus stays on a removed button | High (for affected users) |

<Callout type="bug" title="Why #1 happens: the code only expects data">
A common pattern is "stop loading when items arrive". If the server answers with an empty list `[]`, there are no items, so loading never stops. Developers rarely see it, because their test accounts are full of data. That's why testers should always try a **brand-new account** and an **API that returns `[]`**.
</Callout>

## How to test it

### How to create each state

You can't wait for a real outage. Testers **force** these states on purpose:

<Steps>

1. **First use.** Create a fresh test account (or clear the app's data / reinstall) and visit every list screen before doing anything else.
2. **User cleared.** Delete, archive or complete every item: empty the cart, read all notifications, remove all favorites.
3. **No results.** Search for nonsense ("zzqx"), combine filters that exclude everything, or filter a date range with no data.
4. **No permission.** Log in with a role that has fewer rights, open a link to someone else's data, or deny an OS permission (camera, photos, location) when asked. See <Term id="authorization" />.
5. **Offline.** Turn on <Term id="airplane-mode" /> before opening a screen, and also **while** it loads. Then reconnect and see what recovers by itself. More in [Network conditions](/mobile/network-conditions).
6. **Server errors and edge responses.** With a <Term id="proxy-tool" /> like Charles or Proxyman, use <Term id="map-local" /> to return `[]`, a `500`, a `403`, an empty body or broken JSON, or a breakpoint to delay a response by 30 s to trigger a <Term id="timeout" />. Step by step in [Proxy tools](/mobile/proxy-tools).

</Steps>

<Callout type="tip" title="Go back to 'normal' too">
The recovery is where many bugs hide. After every error, **fix the cause** (reconnect, turn Map Local off) and check the screen **returns to normal** without restarting the app: data appears, banners disappear, nothing is duplicated.
</Callout>

## Accessibility

- **Announce state changes.** When loading ends in an empty or error state, screen reader users must hear it. On iOS and Android, the app should post an accessibility announcement or move focus to the message.
  <DevNote>On the web, put the message in a live region (`role="status"` for empty, `role="alert"` for errors that need attention).</DevNote>
- **Manage focus after Retry.** The Retry button disappears when content loads. Focus should move to the content (or its heading), not get lost at the top of the page.
- **The illustration is decorative.** It should be hidden from screen readers. The **text** carries the meaning.
- **Loading needs words too.** A spinner should have an accessible label like "Loading orders", and the skeleton itself should be hidden from screen readers.
- **Don't rely on color or icons alone.** A red cloud icon without text tells a color-blind or blind user nothing.
- **Contrast and text size.** Grey "helper" text in empty states is often too light: it still needs 4.5:1, and must not be cut off at large text sizes.
- **Buttons are real buttons** with at least 44×44 pt / 48×48 dp touch targets and visible keyboard focus on the web.

## Mobile vs web

<Tabs labels={['iOS', 'Android', 'Web']}>
<Tab>

- Many apps follow the system layout for empty and "no results" states: icon, title, description, optional action.
  <DevNote>SwiftUI has a built-in `ContentUnavailableView` for them (iOS 17+).</DevNote>
- Test with **airplane mode** from Control Center, and with **Low Data Mode** and **Wi-Fi with no internet**.
- Check that denied permissions (Photos, Location) explain how to re-enable them in **Settings**, ideally with a button that opens the app's settings page.
- Use the **Network Link Conditioner** (developer setting) for "100% Loss" and very slow profiles.

</Tab>
<Tab>

- Material guidance: keep empty states simple, with a short message and, where it helps, one action. Pull-to-refresh is a common recovery path, so test it on error screens too.
- Test with **airplane mode**, **mobile data off for this app** (per-app data restriction), and **Data Saver**.
- On the emulator, use the extended controls (**Cellular** settings) to simulate no signal or slow networks.
- Rotate the device and resize on tablets and foldables: the empty state should stay centered and readable.

</Tab>
<Tab>

- Use <Term id="devtools" /> → Network: **Offline** and throttling presets, **Block request URL**, and local overrides to return `[]` or a 500.
- Check the **Console** for errors while empty or error states show, and make sure nothing technical leaks into the page.
- Web apps can also show **error pages** (404, 500). Test a broken URL: is there a friendly page with a way back home, and the right <Term id="http-status-code" />?
- Check the browser **back button** after an error: does it go somewhere sensible?

</Tab>

<KeyTakeaways>

- Every data screen has four states: **loading, data, empty and error**. Exactly one should be visible at a time.
- Empty comes in types (**first use, user cleared, no results, no permission**), and errors in kinds (**offline, server error, timeout**). Each needs its own message.
- A good state says **what happened, why, and what to do next**, with a **Retry or action that really works**, and never shows raw codes or blames the user.
- Force the states yourself: **fresh accounts, deleting everything, airplane mode, and proxy tools returning `[]`, 500 or slow responses**.
- Always test the **way back**: reconnect, retry, clear the filter, and check the screen fully recovers.

</KeyTakeaways>
