Friday evening. Marta orders dinner in a food delivery app while walking to the train. She taps **Place order**, the spinner spins, and she steps into the station elevator. The spinner keeps spinning. She taps again. Back on the street, two confirmation emails arrive: **two dinners, charged twice**.

Nothing was "broken" on the developer's desk, where the office Wi-Fi is fast and never drops. The bug only exists on a real street, with a real phone, on a real network. That's why testing network conditions is one of the most valuable things a mobile tester does.

## Why it matters

- **Most users are not on fast Wi-Fi.** They're on mobile data, moving between cell towers, in basements, on trains and in crowded stadiums.
- **Network bugs cost money and trust.** Double orders, lost photos, prices that are hours out of date, and "Something went wrong" with no way out.
- **Developers rarely see them.** A spinner that never stops looks fine for the 80 ms it's visible on office Wi-Fi.

<Callout type="info" title="The tester's job here">

You're not testing the network. You're testing **how the app behaves when the network is slow, flaky, or gone**, and whether the user always knows what's happening and never loses data.

</Callout>

## Wi-Fi, mobile data and the "G"s

A phone connects to the internet in one of two ways: **Wi-Fi** (a local router, often fast but sometimes overloaded or behind a login page) or **mobile data** (the cellular network). Mobile data comes in generations:

| Network | Typical real-world speed | Typical latency | Where you still meet it |
| --- | --- | --- | --- |
| **2G / Edge** | 0.1–0.25 Mbps | 500–1000 ms | Rural areas, basements, fallback when 4G is overloaded |
| **3G** | 0.5–5 Mbps | 100–500 ms | Older networks (many countries are switching it off), weak signal areas |
| **4G / LTE** | 5–50 Mbps | 30–100 ms | The everyday mobile network for most users |
| **5G** | 50–1000+ Mbps | 10–30 ms | Cities; drops back to 4G indoors and at the edge of coverage |
| **Wi-Fi** | 10–500+ Mbps | 5–50 ms | Home, office, cafés, hotels (quality varies wildly) |

<Callout type="tip" title="The signal icon lies">

"5G" or full bars in the status bar doesn't mean a good connection. A packed stadium on 5G can be slower than a quiet 3G cell. When you report a network bug, write down **how** you simulated the network, not just what the status bar showed.

</Callout>

## Latency, bandwidth and packet loss

These three words describe *how* a connection is bad. Each one breaks apps in a different way.

<NetworkTerms />

A useful rule of thumb: **latency hurts chatty apps** (many small requests in a row), **low bandwidth hurts heavy apps** (big images, videos, uploads), and **packet loss hurts everything unpredictably** (requests stall, then fail or succeed seconds later).

## Real-life situations to recreate

Bad networks aren't just "slow". Here are the situations that find the most bugs:

| Situation | What happens to the network | What to watch in the app |
| --- | --- | --- |
| **Offline** | No connection at all | Clear offline message, cached content, actions queued or blocked politely |
| **Airplane mode** | Wi-Fi and cellular off (Wi-Fi can be turned back on separately) | Same as offline; also test turning it off again: does the app recover by itself? |
| **Switching networks mid-request** | Wi-Fi → cellular when leaving home; the device gets a new IP address and open connections break | In-flight requests fail or hang; uploads and payments must not be lost or duplicated |
| **Elevator / tunnel** | Connection disappears for 10–60 s, then comes back | Spinner forever? Automatic retry? Data lost? |
| **Captive portal** (hotel, airport, train Wi-Fi) | Wi-Fi is "connected" but every request returns the portal's login page (HTML, not JSON) | App shows a helpful error instead of crashing on unexpected HTML |
| **VPN** | Extra latency, different country/IP, some hosts blocked | Region-specific content, login, payments and maps still work |
| **Data Saver / Low Data Mode** | The OS limits background data (Android Data Saver, iOS Low Data Mode) | Background sync, autoplay video and prefetching respect the setting; the app still works |
| **Weak signal / crowded network** | High latency and packet loss | Timeouts, retries, double submits |

<Callout type="example" title="Captive portals are sneaky">

On hotel Wi-Fi the phone shows full Wi-Fi bars, but the app's request to `api.shop.example` gets back an HTML login page (often via a redirect) instead of data. An app that blindly parses the response as <Term id="json">JSON</Term> can crash or show garbage. Try it with a proxy tool that returns HTML for an API call (see [Proxy Tools](/mobile/proxy-tools)).

</Callout>

## What a good app does

A resilient app doesn't need a perfect network. It needs good answers to the question *"what if this request is slow, fails, or never comes back?"*

<Steps>

1. **Shows a loading state.** A <Term id="loading-state">loading state</Term> (spinner or skeleton) appears right away, so the user knows the tap worked. Buttons that send something are disabled while waiting, to prevent a <Term id="double-submit">double submit</Term>.
2. **Uses timeouts.** Every request has a time limit. Without one, a request that lost its packets can hang forever, and the spinner spins forever with it.
3. **Retries sensibly.** Safe requests (loading a list) are retried automatically a few times, waiting a bit longer each time ("backoff"). Payments and orders are only retried if the server can recognize a repeat. This is called <Term id="idempotency" />.
4. **Explains errors in human words.** "You're offline. Check your connection and try again." plus a working **Try again** button. Never `NSURLErrorDomain -1009` or a stack trace. See <Term id="error-message">error messages</Term>.
5. **Shows cached content.** The last loaded data stays visible offline, clearly marked ("Last updated 2 h ago"), instead of an empty screen. Learn more about the <Term id="cache" />.
6. **Queues actions offline.** A sent message, a liked post or a photo upload is saved and sent when the connection returns, with a visible "Waiting to send" state. Or the action is clearly blocked, never silently dropped.
7. **Recovers on its own.** When the network comes back, the app refreshes, hides the offline banner and continues queued work without needing a restart.

</Steps>

<Callout type="tip" title="Things to notice">

- On **Lossy** with no timeout, the app never finds out the request failed. Even with **Retry** on, nothing happens: retries need a timeout to trigger.
- On **Edge** with a **5 s** timeout, every attempt times out, even though the network *would* have delivered in 6.5 s. Timeouts that are too short are bugs too.
- With **Cache** on, users see something useful at 0 s, even offline. But the content may be old, so it must be labeled.

</Callout>

## What to test

### Loading and slowness

- Every screen that loads data shows a loading state on slow 3G. No frozen UI, no blank screen.
- Buttons that send data (Pay, Send, Save) are disabled or show progress while waiting. Tapping twice doesn't create two orders.
- Screens remain usable while images load slowly (text first, images later).
- Long operations show progress, and the user can cancel or leave safely.

### Offline and errors

- Opening the app offline: cached content with an offline indicator, or a friendly offline screen.
- Every error message is human-readable and offers a next step. **Try again** actually tries again.
- Requests time out in a reasonable time. No endless spinners.
- The app recovers automatically when the connection returns (or after one tap on Try again).

### Interruptions and switching

- Switching Wi-Fi → mobile data (and back) during loading, uploading and paying.
- Going offline in the middle of an upload, a form submission and a payment: nothing is lost or duplicated, and the user is told what happened.
- Turning airplane mode on and off with the app in the foreground and in the background. Related: <Term id="interruption">interruptions</Term> and the <Term id="app-lifecycle">app lifecycle</Term>.

### Special networks

- Captive portal Wi-Fi (connected, but no real internet).
- VPN on, especially with a VPN server in another country.
- iOS Low Data Mode / Android Data Saver on.
- Very high latency (1–2 s) with normal bandwidth, and good latency with very low bandwidth.

## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Infinite spinner** | Spinner never stops offline or on a lost request; no timeout, no error | High |
| 2 | **Double submit on slow network** | User taps Pay again because nothing happened; two orders or two payments | Critical |
| 3 | **Technical error text** | `NSURLErrorDomain Code=-1009`, `SocketTimeoutException`, stack traces | Medium |
| 4 | **Silent data loss** | A photo, message or form disappears after the connection drops, with no message | High |
| 5 | **Stale data shown as current** | Old cached prices, balances or stock with no "offline" or "last updated" hint | High |
| 6 | **Dead retry button** | "Try again" does nothing, or only works after restarting the app | Medium–High |
| 7 | **No recovery** | The app stays in the offline state after the network returns | Medium |
| 8 | **Crash on unexpected response** | Captive portal HTML or a truncated response crashes the app | High |
| 9 | **Too-short timeout** | Works on Wi-Fi, always fails on 3G or Edge although the server answers | High |
| 10 | **Race condition after reconnecting** | Old responses arrive late and overwrite newer data. See <Term id="race-condition">race conditions</Term> | Medium |

## How to simulate bad networks

You don't need to ride an elevator all day. Every platform has tools to fake bad networks. Use them to find bugs quickly, then confirm the important ones in the real world.

<Tabs labels={['iOS', 'Android', 'Web views', 'Proxy tools', 'Real world']}>
<Tab>

**Network Link Conditioner on a real iPhone**

<Steps>

1. Enable the **Developer** menu: connect the iPhone to a Mac with Xcode once, then turn on **Settings → Privacy & Security → Developer Mode** (iOS 16 and later) and restart.
2. Open **Settings → Developer → Network Link Conditioner**.
3. Pick a profile such as **3G**, **Edge**, **Very Bad Network**, **High Latency DNS** or **100% Loss**, and turn **Enable** on.
4. Test, then **turn it off again**. It stays on until you do, and it slows down *every* app on the phone.

</Steps>

You can also add your own profile with exact bandwidth, latency and packet loss values.

**From Xcode:** open **Window → Devices and Simulators**, select the connected device and use **Device Conditions → Network Link** to start a profile.

**For the iOS Simulator:** the simulator uses your Mac's network. Install **Network Link Conditioner** from Apple's *Additional Tools for Xcode* download and enable it in System Settings. Remember that it slows down your whole Mac.

</Tab>
<Tab>

**Android Emulator**

<Steps>

1. Open the emulator's **Extended controls** (the **⋯** button in the side toolbar).
2. Go to **Cellular** and set **Network type** (e.g. GSM, EDGE, UMTS/3G, LTE, 5G), **Signal strength** and **Data status** (e.g. turn data off).
3. For offline tests, pull down the quick settings inside the emulator and turn on **Airplane mode**, or turn Wi-Fi and mobile data off separately.

</Steps>

You can also start the emulator with network options, e.g. `emulator -avd Pixel_8 -netdelay gprs -netspeed edge`.

**Real Android devices** have no built-in throttling, so use airplane mode, Wi-Fi/mobile data toggles, **Data Saver** (Settings → Network & internet), a proxy tool, or a router that can limit speed. In **Developer options**, **Mobile data always active** keeps cellular on while Wi-Fi is connected, which affects how quickly the phone can switch networks; test with it on and off if network switching matters.

</Tab>
<Tab>

Many apps show some screens as web pages inside the app (web views), and mobile websites are tested in the browser.

<Steps>

1. Open **Chrome DevTools → Network** (or the **Network conditions** panel).
2. Use the throttling dropdown: presets like **Slow 4G**, **3G** and **Offline**, or add a custom profile with your own download, upload and latency values.
3. For an Android **web view**, connect the device (debug build with web view debugging enabled) and open `chrome://inspect` in desktop Chrome. For iOS web views, use **Safari → Develop** on the Mac (the app must allow inspection).

</Steps>

Throttling in DevTools only affects that browser tab, not the rest of the app. See <Term id="devtools" />.

</Tab>
<Tab>

Proxy tools like **Charles** and **Proxyman** can throttle all traffic from a phone that goes through them:

- **Charles:** **Proxy → Throttle Settings…** → enable throttling and choose a preset (e.g. 3G) or set bandwidth and latency yourself. You can limit it to specific hosts.
- **Proxyman:** **Tools → Network Conditions** → create a rule for a domain with a preset or custom speed.

Proxies can also return errors, empty responses or HTML pages (great for captive-portal tests). Read the next lesson: [Proxy Tools: Charles and Proxyman](/mobile/proxy-tools).

</Tab>
<Tab>

Simulators are great, but nothing beats reality. Plan a short "walking test" for critical flows like checkout, sending messages or uploading:

- Start a payment on Wi-Fi and walk out of range so the phone switches to mobile data.
- Use the app in an elevator, a basement, an underground car park or a train.
- Try a hotel, airport or café Wi-Fi with a login page.
- Turn on a VPN, and try Low Data Mode / Data Saver.
- Test on a <Term id="real-device" /> with a cheap prepaid SIM on a slower network.

Write down where you were and what the phone showed, because real-world bugs can be hard to reproduce.

</Tab>
</Tabs>

<Callout type="warning" title="Don't forget to switch it back">

The most common "bug" reported after network testing is a tester's own phone still running Network Link Conditioner, a proxy or airplane mode. Make "reset network settings" the last step of every network test session.

</Callout>

<KeyTakeaways>

- Test how the app behaves on slow, flaky and missing networks, not the network itself.
- **Latency** slows down chatty apps, **bandwidth** slows heavy content, **packet loss** causes random hangs and failures.
- Good apps show loading states, use timeouts and sensible retries, explain errors in plain words, cache content (clearly labeled) and queue offline actions.
- The biggest risks are infinite spinners, double submits, silent data loss and stale data shown as current.
- Simulate with Network Link Conditioner (iOS), emulator cellular settings (Android), DevTools (web views) and proxy throttling, then confirm critical flows in the real world.
- Always switch simulation tools off when you're done. Related: <Term id="network-throttling" />.

</KeyTakeaways>
