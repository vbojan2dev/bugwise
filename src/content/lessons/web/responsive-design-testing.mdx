A hotel booking site launches its redesign. It looks great on laptops and on phones. Then the support tickets start: *"How do I log in on my iPad?"* Testers had checked a phone (393px wide) and a laptop (1280px wide). Nobody checked an older iPad held upright, which is **exactly 768px** wide. At that one width, the desktop menu disappears and the mobile hamburger button doesn't appear yet. No menu, no **Sign in**, no bookings.

Layouts don't break at the sizes everyone tests. They break **in between**. That's why <Term id="responsive-design" /> needs its own kind of testing.

## Why it matters

- **Most traffic is mobile.** For many shops, banks and delivery services, more than half of all visits come from phones.
- **One page, endless sizes.** The same URL must work on a 320px phone, a tablet in both orientations, a laptop and a 4K monitor.
- **Bugs hide between devices.** A layout can be perfect at 375px and 1280px and broken at 900px, the width of a small laptop window or a tablet in landscape.
- **It's an accessibility topic too.** People who zoom to 200% or enlarge the text get the *mobile* layout on a desktop. If it breaks, they're locked out.

## The core concepts

### The viewport

The <Term id="viewport" /> is the area of the browser where the page is shown. Its width is measured in **CSS pixels**, not physical screen pixels. An iPhone 15 has a screen 1179 physical pixels wide, but its viewport is **393 CSS pixels** wide: each CSS pixel is drawn with 3×3 physical pixels to keep text sharp.

For a phone browser to use that real width, the page needs one line in its HTML `<head>`:

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

<Compare>
<Do title="With the meta viewport tag">

The browser uses the device width (for example 393px), so the mobile layout kicks in and text is readable.

</Do>
<Dont title="Without it">

Mobile browsers pretend the screen is about **980px** wide and shrink the whole desktop page to fit. Text is tiny, and users have to pinch and zoom.

</Dont>
</Compare>

<Callout type="bug" title="Watch out for zoom blocking">
If you see `maximum-scale=1` or `user-scalable=no` in the viewport tag, flag it. It stops pinch-zoom in many browsers, which is an accessibility bug for people with low vision.
</Callout>

### Breakpoints

A <Term id="breakpoint" /> is a width where the layout changes, for example from one column to two. Developers write them as **media queries** in CSS:

```css
/* From 768px and wider: show the navigation links */
@media (min-width: 768px) {
  .nav-links { display: flex; }
  .hamburger { display: none; }
}
```

Every team chooses its own breakpoints. These common values (they're Tailwind CSS defaults) are used in this lesson's demos:

| Name | Applies from | Typical screens |
| --- | --- | --- |
| base | 0px | Phones in portrait (320–430px) |
| sm | 640px | Large phones in landscape, small tablets |
| md | 768px | Tablets in portrait (768–834px) |
| lg | 1024px | Tablets in landscape, small laptops |
| xl | 1280px | Laptops and desktops |

<Callout type="tip" title="Ask for the breakpoints">
Breakpoints are the most valuable test data in responsive testing. Ask the developers or designers for the exact values, or find them yourself in DevTools (more on that below).
</Callout>

### Mobile-first

Most modern sites are built **mobile-first**: the base styles are for the smallest screen, and `min-width` media queries *add* layout for bigger screens. The older **desktop-first** approach starts with the desktop and uses `max-width` queries to *remove* things for smaller screens.

Why should a tester care? Because mixing the two is a classic source of <Term id="off-by-one-error">off-by-one errors</Term>. Look at this:

```css
.nav-links { display: none; }
.hamburger { display: none; }

@media (min-width: 769px) { .nav-links { display: flex; } }   /* 769 and wider */
@media (max-width: 767px) { .hamburger { display: block; } }  /* 767 and narrower */
```

At **exactly 768px**, neither rule applies, and the page has no navigation at all. This is the bug from the hotel story, and it's why you use <Term id="boundary-value-analysis" />: test **at**, **just below** and **just above** every breakpoint.

### Fluid vs fixed layouts

| Layout | How it works | What to watch for |
| --- | --- | --- |
| **Fixed** | Elements have set widths in pixels (`width: 960px`) | Horizontal scrolling on small screens, empty space on big ones |
| **Fluid** | Widths are percentages of the screen (`width: 50%`) | Elements get absurdly wide or squashed at the extremes |
| **Responsive** | Fluid layout plus breakpoints where the design changes | Bugs at and between the breakpoints |

Most real sites are responsive, with a few fixed-width parts mixed in. Those fixed parts (a table, an image, a hero text box) are where layouts usually break.

## What to test

### Layout and navigation

- **Navigation** collapses into a hamburger (or tab bar) on small screens, and the menu opens, closes and scrolls.
- **No horizontal scrolling** at any width from 320px up. Nothing sticks out to the right.
- **Grids** change columns sensibly. No orphaned single cards, no squashed columns.
- **Sticky headers and banners** don't eat the screen. On a small phone, a sticky header plus a cookie banner plus a promo bar can cover half the viewport.

### Content

- **Tables** turn into cards or scroll *inside their own box* instead of widening the whole page.
- **Images** keep their aspect ratio (no stretching or squashing) and aren't blurry on large screens.
- **Text** wraps nicely. Long words, emails and URLs don't overflow (try a German product name).
- **Nothing overlaps**: text on top of images, buttons on top of each other.

### Interaction

- **<Term id="touch-target">Touch targets</Term>** are big enough on mobile: at least 44×44 pt on iOS and 48×48 dp on Android, with space between them. (For websites, WCAG 2.2 sets a lower minimum of 24×24 CSS px, criterion 2.5.8.)
- **No hover-only features.** Menus, tooltips and "quick view" buttons that need a mouse hover are unusable on touch screens.
- **Forms** work with the on-screen keyboard: the focused field isn't hidden behind it, and the right keyboard type shows.

### The edges

- **Smallest supported width:** 320px (older and small phones, split-screen on tablets).
- **Landscape phones:** about 650–930px wide but only 320–430px tall. Sticky headers and modals often don't fit. (See also <Term id="orientation" /> and [Orientation and Screen Sizes](/mobile/orientation-and-screen-sizes).)
- **Zoom and text size:** zoom the browser to **200%** and **400%**, and increase the text size. <Term id="wcag">WCAG</Term> requires content to **reflow** at a width of **320 CSS px** (that's a 1280px screen at 400% zoom) without scrolling in two directions, and text must work at **200%** size without losing content. More in [Accessibility Basics](/web/accessibility-basics).
- **Very large screens:** 1920px and 2560px. Is the content centered with a sensible max width? Are lines of text too long to read? Are images stretched?

## Common bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Gap at a breakpoint** | At exactly one width (often 768 or 1024px) the menu or a section disappears | High |
| 2 | **Horizontal scroll** | The page wiggles sideways on phones; content is cut off on the right | Medium–High |
| 3 | **Wide table** | A table forces the whole page to be wider than the screen | Medium |
| 4 | **Hover-only menu** | A dropdown can't be opened on a phone or tablet | High |
| 5 | **Overlapping content** | Text runs over an image or another element between two breakpoints | Medium |
| 6 | **Content below the fold** | Sticky banners and headers push the main button out of view on small phones | Medium |
| 7 | **Stretched or blurry images** | Product photos lose their proportions or look pixelated on wide screens | Low–Medium |
| 8 | **Tiny touch targets** | Links and icons too small or too close together to tap reliably | Medium |
| 9 | **Broken at 200% zoom** | Text overlaps or gets cut off; buttons disappear | High (for affected users) |
| 10 | **Missing meta viewport** | The phone shows a tiny desktop page | High |

## Tools & how-to

### Chrome DevTools device mode

<Steps>

1. **Open DevTools** with <kbd>F12</kbd> (Windows) or <kbd>Cmd</kbd>+<kbd>Option</kbd>+<kbd>I</kbd> (Mac).
2. **Turn on the device toolbar** with the phone-and-tablet icon, or <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>M</kbd> / <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>M</kbd>.
3. **Pick a size.** Choose a device from the **Dimensions** list, or choose **Responsive** and type any width and height. Drag the handles on the side to resize.
4. **Show the breakpoints.** Open the **⋮** menu in the device toolbar and choose **Show media queries**. Colored bars appear above the page; click one to jump right to that breakpoint. **Show rulers** adds rulers too.
5. **Add your own devices.** Dimensions › **Edit…** › **Add custom device**, for example the exact phones in your analytics.
6. **Rotate** with the rotate icon to test landscape.
7. **Take evidence.** **⋮ › Capture screenshot** saves what you see; **Capture full size screenshot** saves the whole page.

</Steps>

Firefox has **Responsive Design Mode** (<kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>M</kbd> / <kbd>Cmd</kbd>+<kbd>Option</kbd>+<kbd>M</kbd>), and Safari has **Develop › Enter Responsive Design Mode**.

### Test around every breakpoint

Treat each breakpoint like a boundary in a form field ([boundary value analysis](/fundamentals/boundary-value-analysis)). For a breakpoint at 768px, test **767, 768 and 769px**. Do the same for every breakpoint the site has, plus the smallest width you support (320px).

### Resize slowly

Device presets only show you a handful of widths. Also drag the page width **slowly** from your widest to your narrowest size and watch for jumps, overlaps, text that suddenly wraps badly, and a horizontal scrollbar appearing.

<Callout type="tip" title="Find horizontal overflow in one line">
Paste this into the DevTools console. If it says `true`, something is wider than the screen:

`document.documentElement.scrollWidth > document.documentElement.clientWidth`

To find the culprit, look in the Elements panel for the element that sticks out to the right.
</Callout>

### Zoom and text size

- **Browser zoom:** <kbd>Ctrl</kbd>/<kbd>Cmd</kbd> + <kbd>+</kbd> up to 200%, then 400%. At 400% on a 1280px window you're effectively at 320px, so the mobile layout must work.
- **Text-only size:** Chrome **Settings › Appearance › Font size**, Safari on iPhone **aA › bigger A** in the address bar, Firefox **View › Zoom › Zoom Text Only**.
- **Phone settings:** larger text in iOS and Android settings affects many mobile websites too.

### Real phones and tablets

DevTools is fast for checking layouts, but always confirm on at least one real iPhone and one real Android phone, plus a tablet if your users have them. Real devices show the browser toolbars, the notch and <Term id="safe-area" />, the on-screen keyboard and real touch.

### What device mode can't show you

- **It's still your desktop browser.** Choosing "iPhone" in Chrome renders with Chrome's engine, not Safari's. (See [Cross-browser Testing](/web/cross-browser-testing).)
- **No real browser UI:** no collapsing toolbar, no notch, no on-screen keyboard pushing the page up.
- **Touch is simulated with a mouse.** Hover states can still trigger, so hover-only bugs can slip through.
- **Not real performance or screens:** your laptop is much faster, and colors, brightness and pixel density differ from a real phone.

<KeyTakeaways>

- The **viewport** is measured in CSS pixels, and mobile pages need the **meta viewport tag** (without blocking zoom).
- **Breakpoints** are where layouts change. Test **at, just below and just above** each one: that's where off-by-one bugs hide.
- Most sites are **mobile-first**; fixed-width parts inside fluid layouts are where things break.
- Test **navigation, tables, images, text, touch targets, hover, sticky elements, horizontal scroll, landscape, zoom to 200–400%** and **very large screens**.
- Use **DevTools device mode** with custom widths and slow resizing, then **confirm on real phones and tablets**: device mode isn't a real mobile browser.

</KeyTakeaways>
