You're testing a food delivery website. You add a pizza, pay with a test card and see a cheerful green toast: **"Order placed!"** But the order never shows up in *My orders*. You try again. Same thing.

You could write *"Ordering doesn't work"*. Or you could press <kbd>F12</kbd>, open the **Network** panel, and see that `POST /api/orders` came back with **500 Internal Server Error**, while the page showed a success message anyway. Now your bug report says exactly what failed, where, and why it's worse than it looks: users think they ordered food that's never coming.

That's what <Term id="devtools">browser DevTools</Term> give you: an X-ray of the website. You don't need to read code to use them. You just need to know where to look.

## Why it matters

DevTools turn "something is wrong" into evidence a developer can act on:

- **You see what the user can't.** Failed requests, JavaScript errors, slow servers and leaked data are invisible on screen.
- **Your bug reports get better.** A status code, an error message and a request payload save developers hours. Bugs with that evidence get fixed first.
- **You can test things that are hard to reach.** Slow networks, phone screen sizes, long text, logged-out states and hover styles, all from your desk.
- **You can decide who owns the bug.** Wrong data in the response? Backend. Right data shown wrong? Frontend. That's half the triage done.

<Callout type="info" title="Same idea in every browser">
Chrome, Edge, Firefox and Safari all have DevTools. They look slightly different but have the same core panels. This lesson uses **Chrome** names (Edge is almost identical, since it's built on the same engine). Firefox and Safari differences are noted where they matter.
</Callout>

### Elements: inspect and poke the page

The Elements panel shows the live HTML (the **DOM**) on the left and the CSS that applies to the selected element on the right.

What testers use it for:

- **Inspect an element.** Right-click it on the page → **Inspect**, or use the picker icon. You'll see its tag, classes and attributes. Is that "button" really a `<button>`, or a `<div>` that keyboards can't reach? Does the image have `alt` text?
- **Edit text to test long content.** Double-click a text node and type something long: a 60-character product name, a German translation, a name like "Maximiliane Oberhauser-Wittgenstein". Does it wrap, get cut off with an ellipsis, or overflow its card? This is the fastest <Term id="truncation" /> test there is.
- **Check CSS values.** Is the font size really 16px? Is the color the one in the design? The **Computed** tab shows the final value after all rules are applied.
- **Force states.** Hover and focus styles disappear the moment you move the mouse to DevTools. Click **:hov** in the Styles pane (or right-click the node → **Force state**) and tick `:hover`, `:focus`, `:focus-visible` or `:active`. Now you can check that keyboard focus is visible, which is an important <Term id="accessibility-testing" /> check.

<Callout type="warning" title="Your edits are temporary">
Changes in the Elements panel only exist in your browser tab and vanish on reload. That's what makes them safe for experiments. It also means "I changed the HTML and it worked" proves nothing about the real site. Use edits to *explore*, then report what the real page does.
</Callout>

### Console: what crashed behind the scenes

The Console collects messages from the page's JavaScript:

| Level | Looks like | What it usually means for you |
| --- | --- | --- |
| **Error** | Red line, red ✕ icon | Something failed: an exception, a failed request, a blocked resource. Always worth a look. |
| **Warning** | Yellow line, ⚠ icon | Something is deprecated, risky or odd. Often harmless, sometimes an early sign of a bug. |
| **Info / log** | Plain text | Messages developers left on purpose ("Loaded 4 products"). Useful context. |

**What a red error means for your bug report.** An error like `TypeError: Cannot read properties of undefined (reading 'map')` means the code tried to use data that wasn't there, and stopped. If it appears exactly when you click something and that action doesn't work, you've likely found the cause. Copy the message **and** the file and line number on the right (e.g. `app.js:214`). Expand it with the ▸ arrow to see the **stack trace**, which tells developers which functions were running.

Two kinds of red lines show up all the time:

- `Failed to load resource: the server responded with a status of 404 (Not Found)`: the browser couldn't load a file or API call. Check the Network panel for the full story.
- `Uncaught TypeError…` / `Uncaught (in promise)…`: the page's own code crashed.

<Callout type="tip" title="Not every red line is a bug">
A `401 Unauthorized` on `/api/me` when you're logged out may be exactly how the app checks whether you're logged in. Third-party scripts (chat widgets, analytics, ads) often spam warnings. The question is always: **does it match something the user would notice or the requirements forbid?** Clear the console (🚫), do one action, and see what appears. That links the error to your step.
</Callout>

In Chrome, the console is cleared on every page load. Tick **Preserve log** in the Console settings (⚙) when a bug happens just before a redirect, such as after submitting a login form.

### Network: what really happened

This is the panel testers use most. Every row is one request: the HTML page, stylesheets, scripts, images, fonts and the **API calls** (shown as `fetch` or `xhr`) where the real data travels.

The key columns:

- **Name:** the file or <Term id="endpoint" />, e.g. `products?category=fruit`.
- **Status:** the <Term id="http-status-code" />. Failed rows turn red.
- **Type:** `document`, `stylesheet`, `script`, `fetch`, `png`/`webp`…
- **Size:** how much was transferred. `(disk cache)` or `(memory cache)` means it came from the <Term id="cache" />, not the server.
- **Time:** how long it took. Anything over 1 second for an API call deserves attention.

#### Status codes in 30 seconds

| Range | Meaning | Examples you'll see |
| --- | --- | --- |
| **2xx** | Success | `200 OK`, `201 Created`, `204 No Content` |
| **3xx** | Redirect / not modified | `301`/`302` redirect, `304 Not Modified` (use your cached copy) |
| **4xx** | The request was wrong | `400 Bad Request`, `401 Unauthorized` (not logged in), `403 Forbidden` (not allowed), `404 Not Found`, `422` validation error, `429 Too Many Requests` |
| **5xx** | The server failed | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout` |

A **5xx** is almost always a bug. A **4xx** may be correct (wrong password → `401`) or a bug (a valid form → `400`). What matters most is that **the page tells the user the truth** about what happened.

#### Click a row for the details

- **Headers:** the full URL, <Term id="http-method">method</Term> (`GET`, `POST`, `PUT`, `DELETE`), status, and the request and response headers (cookies, content type, caching).
- **Payload:** what the page *sent*, e.g. the form data. Is the right value going out? Is a password visible in a URL? (It should never be.)
- **Preview / Response:** what the server *sent back*, usually <Term id="json" />. Is the data correct? Is there data that **shouldn't** be there, like another user's email or internal fields?
- **Timing:** where the time went. A long **Waiting for server response** (also called TTFB, time to first byte) means a slow server. A long **Content download** means a big response or a slow network.

#### Toolbar features worth knowing

- **Preserve log:** keeps requests when the page reloads or redirects. Essential for login flows, payments and anything that navigates away.
- **Disable cache:** forces a fresh download of every file while DevTools is open. Use it to test what first-time visitors get, and to make sure you're testing the latest <Term id="build" />.
- **Throttling:** the dropdown that says *No throttling*. Pick **Fast 4G**, **Slow 4G**, **3G** or **Offline** to simulate poor connections (<Term id="network-throttling" />). Watch for missing loading states, double submissions and timeouts.
- **Filter by type:** **Fetch/XHR** hides images and scripts so you only see API calls. The text box filters by URL, and supports properties like `status-code:500`, `method:POST` or `-domain:*.analytics.com` (the minus hides matches).
- **Copy as cURL:** right-click a request → **Copy** → **Copy as cURL**. Developers can paste it into a terminal and replay the exact request. It also works in tools like <Term id="postman" /> (see [API Testing with Postman](/web/api-testing-with-postman)).
- **Export HAR:** the download icon (↓) saves every request into a <Term id="har-file" /> (Chrome calls it **Export HAR (sanitized)**). Attach it to bug reports for complex problems.

<Callout type="warning" title="HAR files and cURL commands can contain secrets">
They may include cookies, session tokens and personal data. Recent Chrome versions export a *sanitized* HAR (without cookies and auth headers) by default, but always check before attaching one to a ticket that many people can see. Never post them publicly.
</Callout>

### Application: what the site remembers

The Application panel (called **Storage** in Firefox and Safari) shows what the site keeps in your browser:

- **Cookies:** small values sent with every request, like the session cookie that keeps you logged in. You can see each cookie's expiry and security flags, and edit or delete it.
- **Local storage:** key/value data that survives closing the browser, e.g. a guest shopping cart or theme preference.
- **Session storage:** like local storage, but only for one tab, and gone when the tab closes.
- **Storage › Clear site data:** wipes everything for this site in one click. Perfect for testing as a "brand new visitor".

Deleting a single cookie is a great test: delete the session cookie and click something. Does the site handle it gracefully ("Please log in again") or crash? This panel gets a whole lesson of its own: [Cookies, Sessions and Storage](/web/cookies-sessions-and-storage).

## Device mode, Lighthouse and screenshots

### Device mode (responsive testing)

Click the phone-and-tablet icon in the DevTools toolbar, or press <kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>M</kbd>. The page now renders in a phone-sized <Term id="viewport" />. From the toolbar above the page you can:

- Pick a device preset (iPhone, Pixel, iPad…) or choose **Responsive** and drag the edges to find the widths where the layout breaks (its <Term id="breakpoint">breakpoints</Term>).
- Rotate to landscape, change zoom, and set the device pixel ratio.
- Simulate touch, so taps behave like on a phone.

Device mode is perfect for fast <Term id="responsive-design" /> checks (see [Responsive Design Testing](/web/responsive-design-testing)). But it's still desktop Chrome pretending: it uses Chrome's engine (not iOS Safari's), your computer's CPU, and no real keyboard, notch or browser toolbars. Always confirm important findings on a <Term id="real-device" />.

### Lighthouse

The **Lighthouse** panel runs an automatic audit and scores the page from 0 to 100 in **Performance**, **Accessibility**, **Best Practices** and **SEO**. It also lists concrete problems: images without `alt` text, low <Term id="contrast-ratio" />, huge images, slow <Term id="core-web-vitals" />.

Use <Term id="lighthouse" /> as a quick health check, not a verdict (more in [Performance Basics](/web/performance-basics) and [Accessibility Basics](/web/accessibility-basics)). Run it in an Incognito window (extensions skew the results), run it more than once (scores vary a few points), and remember that a perfect accessibility score doesn't mean the site is accessible. It only catches what a machine can detect.

### Screenshots without extra tools

Open the Command Menu (<kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>P</kbd>), type **screenshot**, and choose:

- **Capture full size screenshot:** the whole page, top to bottom, even the parts you'd have to scroll to. Brilliant for layout bugs on long pages.
- **Capture node screenshot:** just the element selected in Elements.
- **Capture area screenshot:** drag to select a region.
- **Capture screenshot:** the visible part only.

In device mode, the same options appear in the **⋮** menu of the device toolbar, so you can capture a page exactly at phone width.

## What to check with DevTools

Make these part of testing **every** web feature, not just when something looks broken:

- **Console:** clear it before an action. After the action, are there new red errors?
- **Network status codes:** does every API call your action triggers return 2xx? Does the page message match the status (no "Saved!" on a 500)?
- **Duplicate and missing requests:** does one click send exactly one request? Fast double-clicks are a classic way to create duplicate orders (<Term id="double-submit" />).
- **Response data:** is the data correct and complete? Is anything exposed that shouldn't be (password hashes, other users' data, internal notes, tokens)? That's a <Term id="security-testing" /> finding.
- **Performance:** any request over ~1 s? Any huge images or scripts? What happens on **Slow 4G** and **Offline**?
- **Broken resources:** filter for `status-code:404`. Missing images, fonts and scripts often go unnoticed on fast machines.
- **Storage:** what's saved in cookies and local storage? Is it cleared on logout?
- **Layout:** long text via Elements, phone widths via device mode, focus styles via **:hov**.

## Common bugs DevTools reveal

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **False success** | The page says "Saved" but the request returned 4xx/5xx | High |
| 2 | **JavaScript error on an action** | A red `TypeError` in the Console, and the button or filter does nothing | High |
| 3 | **Duplicate requests** | The same API call fires twice per action, sometimes creating duplicates | Medium–High |
| 4 | **Broken image or file** | A red `404` row; a broken image icon or missing icon font on the page | Low–Medium |
| 5 | **Data leak in a response** | JSON includes fields like `passwordHash`, tokens or other users' data | Critical |
| 6 | **Slow endpoint** | One request takes several seconds, mostly "Waiting for server response" | Medium |
| 7 | **Wrong request data** | The payload sends the old value, the wrong ID or a missing field | High |
| 8 | **No loading or error state** | On Slow 4G or Offline, the page freezes or shows nothing at all | Medium |
| 9 | **Stale cache** | The fix only appears with **Disable cache** on; regular users still get the old file | Medium |
| 10 | **Sensitive data in the URL** | A password, token or email appears in a request URL (and ends up in logs and history) | High |

## A DevTools routine for every test session

<Steps>

1. **Open DevTools before you start**, docked at the bottom. Open the Network panel and keep the Console's error count in view.
2. **Tick Preserve log and Disable cache** so you keep evidence across redirects and always test the latest files.
3. **Clear the Console and Network log before each important action** (🚫). Then every new line belongs to your step.
4. **Do the action once, slowly.** Check: new red errors? Status codes? One request or two? Payload and response correct?
5. **Repeat under stress:** Slow 4G, Offline, a phone width in device mode, long text via Elements.
6. **Collect evidence when you find a bug:** a screenshot (Command Menu › Capture screenshot), the console error text, the request URL, status, payload and response, and if needed a HAR file or cURL command.

</Steps>

Then write it up using the structure from [How to Write Bug Reports](/tutorials/writing-bug-reports).

<KeyTakeaways>

- Open DevTools with <kbd>F12</kbd> or <kbd>Cmd</kbd>+<kbd>Option</kbd>+<kbd>I</kbd>. In Safari, switch on **Show features for web developers** first.
- **Elements:** inspect, edit text to test long content, check CSS, force `:hover` and `:focus`. Edits are temporary.
- **Console:** red errors that appear right when an action fails usually explain why. Copy the message, file and line.
- **Network:** check status codes, count requests, read payloads and responses, check timing. Use Preserve log, Disable cache, throttling, Fetch/XHR, Copy as cURL and HAR export.
- **Application:** see and delete cookies and storage, or clear site data to test as a new visitor.
- Use device mode, Lighthouse and full-size screenshots for quick checks, and remote debugging to inspect real phones.
- The best DevTools bugs are the invisible ones: false successes, duplicate requests, data leaks and slow endpoints.

</KeyTakeaways>
