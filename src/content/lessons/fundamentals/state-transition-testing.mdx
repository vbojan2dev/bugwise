Maya orders a pair of running shoes. They arrive on Tuesday, she wears them on Wednesday, and on Thursday she opens the shop app out of curiosity. The **Cancel order** button is still there. She taps it. The app says "Order canceled", and three days later **$84 lands back on her card**. She keeps the shoes.

Nobody wrote code that said "give away free shoes". The developer simply forgot to ask one question: *should Cancel still work when the order is already delivered?* The button did the same thing in every situation, when it should have depended on **where the order was in its journey**.

That question is the whole idea behind <Term id="state-transition-testing">state transition testing</Term>.

## What is state transition testing?

Some features always react the same way: a calculator adds 2 + 2 the same way every time. Many others **remember where they are**, and the same action gives a different result depending on that. Tapping **Cancel** on a fresh order should cancel it. Tapping it on a delivered order should not.

State transition testing is a <Term id="black-box-testing">black-box</Term> test design technique for those features. You draw the places the system can be in (its **states**), the things that move it between them (**events**), and then you test both the moves that *should* happen and the ones that *should not*.

<Callout type="example" title="An everyday analogy: the washing machine">

A washing machine is always in one state: **Idle**, **Washing**, **Spinning** or **Done**. Pressing **Start** in Idle starts a wash. Pressing **Start** while it is already washing does nothing. And pulling the door handle mid-wash must *not* open the door, or your bathroom floods.

Same button, same handle, different results, all depending on the state. Engineers who build washing machines think this way, and testers should too.

</Callout>

### The building blocks

| Word | Meaning | Music player example |
| --- | --- | --- |
| **State** | A situation the system is in, which changes how it reacts | Stopped, Playing, Paused |
| **Event** | Something that happens: a tap, a timer, a server message | The user taps Pause |
| **Transition** | A move from one state to another, caused by an event | Playing → Paused |
| **Guard** | A condition that must be true for the transition to happen | Refund only if delivered ≤ 30 days ago |
| **Action** | What the system does while it moves | Remember the playback position |

## The quick version

### Two ways to write it down

A **state diagram** (like the one above) is great for seeing the flow. A **state table** is great for finding gaps. It lists every state as a row and every event as a column, so you're forced to answer *"what if this event happens in this state?"* for every single combination:

| State ↓ / Event → | Play | Pause | Stop |
| --- | --- | --- | --- |
| **Stopped** | Playing | ✕ ignore | ✕ ignore |
| **Playing** | ✕ ignore | Paused | Stopped |
| **Paused** | Playing | ✕ ignore | Stopped |

Every **✕** cell is an **invalid transition**: the event must be rejected or ignored, and the state must not change. Diagrams quietly hide those cells. Tables put them in front of you.

### How much to test: three levels of coverage

<Steps>

1. **Every state.** Make sure you visit each state at least once. The weakest level.
2. **Every valid transition.** Fire each arrow on the diagram at least once. This is the usual minimum for a feature.
3. **Every invalid transition.** Try each ✕ cell and check the system says no. This is where the expensive bugs are.

</Steps>

### Where it shines

Anything with a **status** or a **mode** in a mobile or web app:

- **Orders:** Placed → Paid → Shipped → Delivered, plus Canceled and Refunded. See [shopping cart and checkout](/features/shopping-cart-and-checkout).
- **Login lockout:** 0, 1, 2 wrong passwords, then Locked for 15 minutes. See [login and sign-up](/features/login-and-sign-up).
- **Players and trackers:** Stopped / Playing / Paused, or a workout that is Running / Paused / Finished.
- **Trips and deliveries:** a ride that is Requested → Driver assigned → On trip → Completed.
- **Cards and accounts:** Active, Blocked, Expired.

### Typical bugs it finds

- An invalid transition is **allowed**: canceling a delivered order, paying twice, refunding an unpaid order.
- A **stuck state**: the order stays "Processing" forever after a network error, and no button gets you out.
- The **wrong state after restart**: you pause a workout, the app is killed in the background, and it comes back "Running". See [background and foreground](/mobile/background-and-foreground).

## The building blocks in depth

### States

A state is a **situation that changes how the system reacts to the same input**. That definition is the test for whether something deserves to be a state.

- "The order is paid" is a state, because Pay, Cancel and Refund all behave differently once it's true.
- "The order has a blue shipping label" is not a state if nothing behaves differently because of it.

Two special kinds of state appear in almost every model:

- The **initial state** is where the system starts: a new order is Placed, a fresh login screen has 0 wrong attempts. On a diagram it's marked with a small filled dot and an arrow.
- A **final state** is one the system never leaves: a Canceled or Refunded order. It's drawn with a double border. Final states are great places to test, because *every* event there should be rejected.

<Callout type="note" title="States are not screens">

Beginners often draw one state per screen. That's a different thing. The Order details **screen** can show an order in six different **states**, and the Logged in state can span fifty screens. Ask "does the system behave differently?", not "does the screen look different?".

</Callout>

### Events and transitions

An **event** is anything that can happen to the system. Some come from the user (tap Cancel), some from time (15 minutes pass, the paid parking time runs out), and some from other systems (the courier's scanner says "delivered", the bank confirms a payment, a <Term id="push-notification" /> arrives).

A **transition** is the arrow: *in state A, when event E happens, go to state B.* A transition can also go back into the **same** state. A bank card that is Active stays Active after a successful payment, but something still happens: money moves. That's called a self-transition.

### Guards

A **guard** is a yes/no condition written in square brackets on an arrow, like `refund [≤ 30 days since delivery]`. The same event in the same state can go different ways depending on the guard:

- Delivered + Refund **[within 30 days]** → Refunded
- Delivered + Refund **[after 30 days]** → stays Delivered, with the message "The return window has closed"

Guards are where state transition testing meets <Term id="boundary-value-analysis" />: test day 30 and day 31, not just day 5. And where several conditions combine (amount, country, membership level), a <Term id="decision-table" /> is the better tool for the guard itself. See [boundary value analysis](/fundamentals/boundary-value-analysis) and [decision tables](/fundamentals/decision-tables).

### Actions

An **action** is what the system *does* during a transition: charge the card, send the tracking email, reset the counter, release the reserved stock. Written after a slash: `cancel / refund payment`.

Actions matter because a transition can land in the right state and still do the wrong thing. If canceling a paid order shows "Canceled" but never refunds the money, the state is correct and the customer is still out $84. Always check the **state** and the **action** in your <Term id="expected-result">expected result</Term>.

## Drawing a state diagram from a spec

You don't need special software. Paper, a whiteboard or any diagram tool works. Here's the method, using an online shop's order rules.

<Steps>

1. **Find the nouns that describe a status.** Read the <Term id="requirement">requirements</Term> and highlight words like *placed, paid, shipped, delivered, canceled, refunded*. Those are your candidate states.
2. **Find the verbs and the timers.** *Pay, ship, deliver, cancel, refund, 30 days pass.* Those are your events.
3. **Draw the happy path first.** Placed → Paid → Shipped → Delivered.
4. **Add the side exits.** Where can the order be canceled? Where can it be refunded? Add guards and actions as you go.
5. **Mark the initial and final states.** Where does it start? Which states are dead ends?
6. **Turn it into a table and look at the empty cells.** Every empty cell is a question for the product owner: "What should happen if a customer taps Cancel while the order is Shipped?" If nobody knows, you've found a gap in the spec before writing a single test.

</Steps>

## State tables: where the bugs hide

The diagram above has 6 states and 5 events. That's 6 × 5 = **30 combinations**, but only **6 arrows**. The other 24 combinations are invalid transitions. A diagram doesn't show them, so nobody thinks about them. A state table does.

You'll build the full order table in the explorer below (switch it to **State table**). Here's a compact version of the most interesting rows:

| State | Cancel | Refund | Pay |
| --- | --- | --- | --- |
| **Placed** | Canceled | ✕ nothing was paid | Paid |
| **Paid** | Canceled / refund | ✕ use Cancel | ✕ already paid |
| **Shipped** | ✕ offer a return | ✕ not delivered | ✕ already paid |
| **Delivered** | ✕ too late | Refunded [≤ 30 days] | ✕ already paid |

For every ✕ cell, a correct system does three things:

1. **Stays in the same state.** Nothing moves.
2. **Does no action.** No money moves, no email is sent, no stock is released.
3. **Tells the user why** (if the user caused it), or hides/disables the control in the first place. See [buttons](/components/button) and their <Term id="disabled-state">disabled state</Term>.

<Callout type="warning" title="Hidden buttons are not enough">

A good app hides the Cancel button on a delivered order. But testers know the button isn't the only way in: a second browser tab opened earlier, an old link in an email, the app's <Term id="api" />, a slow network that lets you tap twice. The **server** must reject invalid transitions too, not just the UI. When you can, test both.

</Callout>

## How much to test: coverage levels

<Term id="test-coverage">Coverage</Term> tells you how much of the model your tests have touched. From weakest to strongest:

| Level | What you test | Order example |
| --- | --- | --- |
| **All states** | Each state at least once | 6 states, reachable in 2 tests (one ending in Canceled, one in Refunded) |
| **All valid transitions** | Each arrow at least once | 6 arrows, coverable in 3 tests; the usual minimum |
| **All invalid transitions** | Each ✕ cell at least once | 24 cells, the high-value negative tests |

Visiting every state is **not** enough. You can visit all six order states without ever trying "cancel a paid order", and miss that it forgets to refund.

<Callout type="info" title="Going further: 0-switch and 1-switch coverage">

In ISTQB terms, these levels are called *all states coverage*, *valid transitions coverage* and *all transitions coverage* (every valid transition fired **and** every invalid one tried). You may also see the terms **0-switch** and **1-switch** coverage. **0-switch** means testing every single transition on its own (the "all valid transitions" level above). **1-switch** means testing every *pair* of transitions in a row, such as Paid → Shipped followed by Shipped → Delivered. Pairs catch bugs where the second step depends on how you got there. For most manual testing, all valid transitions plus the risky invalid ones is the sweet spot; reach for 1-switch on payment or safety-critical flows.

</Callout>

## Where it shines in mobile and web apps

<Tabs labels={["Orders", "Login lockout", "Ride-hailing", "Bank card"]}>
<Tab>

**Order status** is the classic. The same rules usually show up in three places: the customer app, the staff back office, and emails or push notifications. Each one is a door into the same state machine. Things to try:

- Cancel at every state, not just Placed.
- Pay twice: double-tap Pay, or pay from two tabs. This is a <Term id="double-submit" /> and the server needs <Term id="idempotency" /> to stop it.
- Refund at every state, especially before payment and after the 30-day guard.

More in [shopping cart and checkout](/features/shopping-cart-and-checkout).

</Tab>
<Tab>

A **login with lockout** turns a counter into states: 0 wrong, 1 wrong, 2 wrong, Locked. It protects against a <Term id="brute-force-attack" />.

- The third wrong password locks the account (not the second, not the fourth: a boundary!).
- The **right** password while Locked must still be rejected.
- A successful login resets the counter. Does it? Test 2 wrong → right → log out → 1 wrong: the account must not lock.
- After 15 minutes, can you log in again? What if you kill the app during the lockout?

More in [login and sign-up](/features/login-and-sign-up).

</Tab>
<Tab>

A **ride-hailing trip** has states driven by three different people: the rider, the driver and the system.

- Paying while **Blocked** must be declined. This is the whole point of the freeze button.
- Unblock needs Face ID or the PIN (the guard). Test it with the check failing.

## Turning transitions into test cases

Each transition (valid or invalid) becomes one <Term id="test-case" />. The structure maps neatly:

| Test case part | Comes from |
| --- | --- |
| <Term id="precondition">Precondition</Term> | The **start state** (and how to get there) |
| Step | The **event** (and the guard value) |
| Expected result | The **end state** + the **action** (or "stays, nothing happens") |

<Steps>

1. **Pick a transition**, for example Paid + Cancel.
2. **Write the precondition as a path from the initial state:** "Order placed and paid with a test card."
3. **Write the step:** "Tap Cancel order and confirm."
4. **Write both halves of the expected result:** "Status is Canceled **and** a refund of $84.00 appears in Payments."
5. **Chain transitions to save time.** One test can walk Placed → Paid → Shipped → Delivered → Refunded and check each step. Just make sure a failure in step 2 doesn't hide steps 3 to 5.

</Steps>

<Callout type="tip">

For invalid transitions, write the expected result as "**stays** in Shipped, no refund, message 'This order has already shipped'". "Nothing happens" on its own is too vague: you want to check that the state, the money **and** the message are right. More on writing good steps in [writing test cases](/tutorials/writing-test-cases).

</Callout>

## Typical bugs

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | Invalid transition allowed | Delivered order can be canceled and refunded | Critical |
| 2 | Paying twice | Double-tap Pay, card charged twice | Critical |
| 3 | Refund on an unpaid order | Refund issued for money never received | Critical |
| 4 | Lockout ignores the right password | Locked account still logs in with the right password | Critical |
| 5 | Stuck state | Order stays "Processing" forever after a network error | Major |
| 6 | Wrong state after restart | Paused workout comes back as Running after the app is killed | Major |
| 7 | Action missing | Order shows Canceled but no refund is made | Major |
| 8 | Final state revived | Old payment link re-opens a canceled order | Major |

Bugs 5 and 6 deserve a special mention for mobile. Apps are paused, killed and restored all the time, and the state must come back correctly from the server or from saved data. That's <Term id="state-persistence" /> and <Term id="state-restoration" />. Test transitions **across** a restart: start in Paused, kill the app, reopen, and check you're still in Paused. See [background and foreground](/mobile/background-and-foreground) and [interruptions](/mobile/interruptions).

When you find one of these, the state table makes your [bug report](/tutorials/writing-bug-reports) easy to write: start state, event, expected state, actual state.

## When to use it (and when not to)

**Use it when** the same input gives different results depending on history: statuses, modes, counters, wizards, sessions, players, anything with "if it's already X, then…".

**Skip it when** the feature has no memory: a unit converter, a tip calculator, a search box. There, <Term id="equivalence-partitioning" /> and <Term id="boundary-value-analysis" /> do the work.

<Callout type="info" title="Same idea, different names">

You'll also hear *state machine*, *finite state machine*, *state model* and *lifecycle*. They describe the same thing. The [bug life cycle](/fundamentals/bug-life-cycle) itself is a state machine: New → Assigned → Fixed → Retest → Closed, with Reopened as the path back when a retest fails.

</Callout>

<KeyTakeaways>

- Use state transition testing when the same action gives different results depending on where the system is: orders, logins, players, trips, cards.
- The building blocks are **states**, **events**, **transitions**, **guards** (conditions in brackets) and **actions** (what happens during the move).
- Diagrams show the flow; **state tables** expose every "what if this event happens in this state?" combination.
- Coverage grows from **all states** to **all valid transitions** to **invalid transitions**. The invalid ones find the costly bugs.
- Each transition becomes a test case: start state as precondition, event as step, end state **plus action** as expected result.
- Watch for allowed invalid transitions, stuck states and the wrong state after an app restart.

</KeyTakeaways>
