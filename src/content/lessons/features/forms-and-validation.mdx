Siobhán O'Brien wants to order groceries. She downloads the app, taps **Create account** and types her name. "Name can only contain letters." She tries "Siobhan OBrien", then her email `siobhan+food@mail.ie`. "Enter a valid email address." She gives up and orders from a competitor. Nobody at the company ever hears about it. In the analytics it's just one more person who "dropped off at sign up".

Forms are where users **give** an app something: their name, their address, their money. Every sign up, checkout, booking, support request and profile screen is a form. A broken form doesn't crash. It quietly turns customers away, which is why testers who know forms well are so valuable.

## The quick version

### What a good form looks like

- Every field has a **visible label** above it. A <Term id="placeholder" /> disappears when you type, so it can't be the label.
- Rules and formats are explained **before** typing ("For example SW1A 1AA"), not only after a mistake.
- Optional fields are marked "(optional)", related fields are **grouped** under a heading.
- Each field opens the **right keyboard** (email, phone pad, numbers) and has an **autocomplete** hint, so <Term id="autofill">AutoFill</Term> and password managers can fill it.

### Two layers of validation

<Term id="input-validation" /> happens twice. **<Term id="client-side-validation">Client-side</Term>** checks run in the app or browser and give quick feedback. **<Term id="server-side-validation">Server-side</Term>** checks run on the server and are the only ones you can trust, because anyone can skip the app and send data straight to the API. As a tester, check both: a rule that only exists in the app is a bug waiting to happen.

### When to show errors

Show an error **when the user leaves a field** (on blur) or **on submit**, then update it live while they fix it. Don't **shout while they're still typing**: "Invalid email" after the first letter is rude and useless.

### Error messages that help

A good <Term id="error-message" /> is **next to the field**, says **how to fix it** in plain words ("Enter a postcode like SW1A 1AA"), uses **text and an icon, not only red**, and is **announced to screen readers**. After an error, everything the user typed **stays** in the form.

### Test real-world data

The world is bigger than "John Smith, 12345":

- Names: `O'Brien`, `Đorđe Petrović`, `Anne-Marie`, a single name like `Sukarno`, very long names.
- Emails: `anna+shop@mail.com`, `anna@mail.co.uk`, uppercase letters.
- Phones and postcodes: `+44 7700 900123` with spaces, `SW1A 1AA`, `1012 AB`.
- Dates and ages: the 18th birthday **today**, 29 February.
- Spaces before and after, pasted text, emoji, and decimal commas (`1,5`).

### Whole-form behavior

Tap **Submit** twice, submit with the server failing, let the session time out, press **Back**. The form must not create duplicates, lose the user's data or show a frozen spinner.

## How it works

Behind every **Create account** or **Place order** button, the same journey happens:

<Steps>

1. **The user fills in the form.** Typing, picking from lists, pasting, or letting AutoFill do it. The app may check fields as they go (client-side validation).
2. **The user submits.** The app checks everything once more. If something is wrong, it shows the errors and sends nothing.
3. **The app sends the data.** Usually a `POST` request with the values in the body, over HTTPS. The submit button shows a <Term id="loading-state" /> and can't be used again until there's an answer.
4. **The server validates again.** Same rules, plus checks only the server can do: is this email already registered? Is this postcode one we deliver to? Too many sign ups from this device?
5. **The server answers.** Success (for example `201 Created`), a validation error with details per field (often `400` or `422`), or a server error (`500`). See <Term id="http-status-code">HTTP status codes</Term>.
6. **The app shows the result.** A success screen or confirmation, or the errors next to the right fields, **with everything the user typed still there**.

</Steps>

### Client-side vs server-side validation

<ValidationLayers />

Client-side validation is a **convenience** for the user. Server-side validation is **protection** for the business. A developer can forget to add a rule to the app, the iOS and Android apps can have different rules, an old app version can have no rules at all, and anyone can send a request with a tool like [Postman](/web/api-testing-with-postman) or change it on the way with a <Term id="proxy-tool" />. Only the server sees every request.

| Rule | Client-side | Server-side |
| --- | --- | --- |
| Required fields, formats, lengths | Yes, for quick feedback | Yes, always again |
| "This email is already registered" | No (only the server knows) | Yes |
| Price, discount, stock | Display only | Yes, the server decides |
| Too many attempts from one device | No | Yes (<Term id="rate-limiting" />) |

<Callout type="bug" title="How testers find missing server checks">

Find a rule the app enforces (for example "name max 50 characters") and send the same request **without the app**: replay it in [DevTools](/web/devtools-for-testers) with a 300-character name, or send it from Postman. If the server says `201 Created`, the rule exists only on the surface. Typical results: broken layouts in the admin panel, crashes in other apps that read the data, and sometimes security holes such as <Term id="xss" /> or <Term id="sql-injection" />.

</Callout>

## Anatomy of a good form

<FormAnatomy />

### Labels, placeholders and help text

The label says **what** to enter; help text says **how**. Both stay visible while the user types. A placeholder is at most an extra example, because it vanishes on the first keystroke and often has low contrast (more on the [Text Field](/components/text-field) page). Put formats and rules **before** the field ("At least 8 characters", "For example 27 3 1995"): users shouldn't have to fail once to learn the rules.

### Required and optional

Pick one convention and use it everywhere. Most forms have fewer optional fields, so many teams mark those with "(optional)" and say so at the top. If the team uses an asterisk (`*`) for required fields instead, it must be explained ("* required") and announced by screen readers, not just a red star. Test that what's **marked** required is what's **actually** required: a field marked optional that blocks submit, or a "required" field the server happily accepts empty, is a bug.

### Grouping and order

Related fields belong together under a heading: "About you", "Delivery address", "Payment". Screen readers should announce the group's heading when you enter it. The order should match how people think (name before address, street before city), and the keyboard's **Next** or **Tab** key should follow the same order (<Term id="focus-order" />). One column is easier to scan than two, especially on phones.

### Input types and mobile keyboards

The field type decides which keyboard appears on a phone:

| Field | Web | What appears on a phone |
| --- | --- | --- |
| Email | `type="email"` | Keyboard with `@` and `.` |
| Phone | `type="tel"` | Phone pad with `+` |
| Whole numbers (PIN, code) | `inputmode="numeric"` | Number pad |
| Amounts, weights | `inputmode="decimal"` | Number pad with `.` or `,` (depends on the region) |
| Web address | `type="url"` | Keyboard with `/` and `.com` |

A keyboard is only a **hint**: people paste, use hardware keyboards and autofill, so a "numbers only" field still needs validation. The [Text Field](/components/text-field) page has a live keyboard demo.

### Autocomplete and autofill

Browsers, iOS, Android and <Term id="password-manager">password managers</Term> can fill a whole form in one tap, but only if each field says what it contains. On the web that's the `autocomplete` attribute: `name`, `email`, `tel`, `street-address`, `address-level2` (city), `postal-code`, `country`, `bday`, `new-password`, `one-time-code` and more. The [Text Field](/components/text-field) page has a table of the most common hints.

<Callout type="dev" title="Names in code">

Groups on the web are a `<fieldset>` with a `<legend>`. The keyboard is set with `type` and `inputmode` on the web, `keyboardType` on iOS and `inputType` on Android. Autofill hints are `autocomplete` on the web, `textContentType` on iOS and `autofillHints` on Android. Error messages are linked to fields with `aria-invalid="true"` and `aria-describedby`.

</Callout>

What to test:

- **AutoFill puts each value in the right field.** A wrong token is easy to miss in code review: the city lands in the postcode, the surname in the first name.
- **Autofilled values pass validation.** Autofill can add a country code, a trailing space or a format your rules don't expect.
- **The form notices the values.** Some forms only react to typing, so autofilled fields still count as "empty" or the button stays disabled.
- **Sign up offers a strong password** and the new password is saved to the password manager afterwards (`autocomplete="new-password"`).
- **Fields about the user have tokens.** On the web this is a WCAG requirement: 1.3.5 Identify Input Purpose (AA).

## When to validate

There are three moments to check a field. Each has trade-offs (try them live on the [Text Field](/components/text-field) page):

| Timing | Good for | Problem |
| --- | --- | --- |
| **On submit** | Short forms; simple to build | Users discover all problems at the end |
| **On blur** (when leaving the field) | Most fields; the usual best default | Can fire too early if the user just taps around |
| **While typing** | Password rules checklist, character counters, "username available" | Shouts at people before they've finished |

<Callout type="tip" title="The rule: don't shout while the user is still typing">

`a` is not a valid email, and neither is `anna@`. That's because the user hasn't finished. Showing "Invalid email" from the first letter is like a waiter saying "wrong order" while you're still reading the menu. The usual pattern is **"late to complain, quick to forgive"**: show an error only when the user leaves the field or submits, but once an error is showing, re-check on every keystroke so it **disappears the moment the value is fixed**.

</Callout>

Whatever the team chooses, test that it's **consistent** across the form, that errors **clear** as soon as the value is fixed, that tapping into an empty field and out again doesn't immediately paint everything red, and that **submit always validates everything**, including fields the user never touched.

A good error message:

- **Is specific and tells the user what to do.** "Enter a postcode like SW1A 1AA", not "Invalid input" or "Error 422". (WCAG 3.3.3 Error Suggestion, AA.)
- **Sits next to the field** it's about, and the field is visually marked.
- **Uses plain language.** No codes, no blame ("You entered an illegal value"), no jargon ("Regex mismatch").
- **Isn't color only.** Red plus text plus an icon, so people who can't see red still notice it. (WCAG 1.4.1 Use of Color, A, and 3.3.1 Error Identification, A.)
- **Reaches screen reader users.** The field is announced as invalid and the message is read out with it. After a failed submit, focus moves to the first invalid field **or** to an **<Term id="error-summary">error summary</Term>** at the top that lists every problem as a link. Each link must move focus to its field.
- **Keeps the user's input.** Nothing typed is cleared after an error. Many teams clear the password on purpose; if so, say so and keep everything else.
- **Disappears when the problem is fixed**, and comes back if it's broken again.

Server errors need the same care. "Something went wrong" with no next step is a dead end. Better: "We couldn't create your account right now. Your details are saved, please try again in a minute." And if the server rejects one field ("This email is already registered"), the message belongs **next to that field**, not in a generic toast.

<Callout type="note" title="Sign up and account enumeration">

"This email is already registered" tells an attacker who has an account. [Login and Sign Up](/features/login-and-sign-up) explains the trade-off and the safer alternatives. Check which one your spec asks for.

</Callout>

## Data formats and edge cases

Most "invalid input" bugs are really **valid input the developer didn't expect**. Keep these lists handy as <Term id="test-data" />.

### Names

| Try | Why |
| --- | --- |
| `O'Brien`, `D'Angelo` | Apostrophes are part of many surnames |
| `Đorđe Petrović`, `Zoë`, `José`, `Łukasz` | Letters with <Term id="diacritics" /> must be accepted **and** displayed correctly later |
| `Anne-Marie`, `García Márquez`, `van der Berg` | Hyphens, two surnames, lowercase particles |
| `Sukarno` (one name) | Many people have a single name. "First name" and "Last name" both required blocks them |
| A 70-character name | Long names exist. Check the limit, the error, and every screen and email that shows the name |
| `王芳`, `Јована` | Other scripts, if the product supports those markets |

Two separate fields for first and last name don't fit every culture. A single **Full name** field is often simpler. If the spec splits them, test what happens to single names and long double surnames.

### Emails

- **<Term id="plus-addressing">Plus addressing</Term>:** `anna+groceries@mail.com` is valid and widely used to filter mail. Rejecting `+` is one of the most common form bugs.
- **Subdomains and long domains:** `anna@mail.example.co.uk`, `anna@company.photography`.
- **Dots and dashes:** `anna.maria-k@mail.com`.
- **Length:** the part before `@` can have up to 64 characters, and a whole address up to 254 in practice. Test a long but valid one.
- **Case and spaces:** `Anna@Mail.com` and a trailing space from autofill should be cleaned up, not rejected.
- **Typos:** `anna@gmial.com` is valid but wrong. Some apps suggest "Did you mean gmail.com?". Nice to have, not a validation rule.

### Phone numbers

People type phone numbers the way they see them: `+44 7700 900123`, `+385 (91) 234-5678`, `0049 151 1234567`. The international format (E.164) has up to 15 digits after the `+`. A good form accepts spaces, dashes and brackets, **removes** them before saving, and either asks for the country or offers a country code picker. Test with numbers from every market the product serves, and never rely on a 10-digit limit.

### Postcodes by country

| Country | Example | Format |
| --- | --- | --- |
| United States | `94103`, `94103-1234` | 5 digits, optional ZIP+4 |
| United Kingdom | `SW1A 1AA`, `M1 1AE` | Letters and digits, with a space, different lengths |
| Netherlands | `1012 AB` | 4 digits, space, 2 letters |
| Canada | `K1A 0B6` | Letter-digit-letter, space, digit-letter-digit |
| Germany, Croatia | `10115`, `10000` | 5 digits (a leading 0 is possible in Germany: `01067`) |
| Hong Kong | none | No postcodes at all: the field must be optional there |

The postcode rule must **depend on the selected country**, and changing the country should re-check the postcode. A leading zero (`01067`) is a classic: if the field is stored as a number, it becomes `1067`.

### Dates and ages

- **The birthday boundary:** with an 18+ rule, someone whose 18th birthday is **today** is allowed. Test the day before, the day itself and the day after. This is <Term id="boundary-value-analysis" />, and the classic bug here is an <Term id="off-by-one-error" />.
- **29 February:** when does someone born on 29 February 2008 turn 18 in a non-leap year? The answer depends on the country's law. Ask, then test it.
- **Impossible dates:** `31 2 1995` should be rejected with a message, not silently become 3 March (see [Date Picker](/components/date-picker)).
- **Day and month order:** `03/04/2005` is 3 April in Europe and March 4 in the US. Separate Day, Month and Year boxes, or a date picker, avoid the confusion.
- **Future and unrealistic dates:** born in 2090 or in 1850.

### Numbers, decimals and amounts

`1,5` is one and a half in Germany, Croatia and much of Europe; `1.5` in the US and UK. In an amount field, `1,500` can mean fifteen hundred or one and a half. Test with the device set to different regions (see [Localization and RTL](/features/localization-and-rtl)), and check that `0`, negative numbers, very large numbers and leading zeros are handled as the spec says.

### Spaces, paste, emoji and formatted text

- **Leading and trailing spaces** should be trimmed before validating and saving. Spaces **inside** a password are part of it and must be kept.
- **Spaces only** in a required field should count as empty.
- **Paste** must work everywhere, including password and "confirm" fields. Paste a value with a line break at the end (it happens when copying from emails and PDFs).
- **Formatted text** from Word, a PDF or a website can bring curly quotes (`’` instead of `'`), non-breaking spaces and invisible characters. `O’Brien` with a curly apostrophe must work too.
- **Emoji** in names, notes and addresses: accepted or rejected with a clear message, never stored as `???`.
- **Length limits on paste:** if a field has a maximum, pasting a longer value shouldn't cut it silently (see <Term id="truncation" />).

## Multi-step forms, double submit and server errors

### Multi-step forms and saving progress

Long forms (insurance quotes, loan applications, checkouts) are often split into steps, a <Term id="wizard" />. Test that **Back** keeps what was entered, that you can't skip a required step, that the step indicator is right, and that a draft survives a refresh or a closed app if the spec promises it. The [Wizard](/components/wizard) page has a full bug hunt on this. For long forms, ask whether progress is saved on the server or only on this device: a draft that exists only on the phone is gone when the user switches to the laptop.

### Preventing double submit

A slow network, an impatient user, and a button that stays active: that's a <Term id="double-submit" />, and it creates two accounts, two bookings or two support tickets. The fix has two layers. The **app** disables the button and shows a loading state as soon as it's pressed (and pressing **Enter** again must not send another request either). The **server** recognizes a repeated request, for example with an idempotency key (see <Term id="idempotency" />). Test with the network throttled: tap twice, press Enter twice, tap and press Enter.

### Server errors and lost connections

What happens when the server answers `500`, or the connection drops after you tap **Submit**? The user should see a clear message, **all their input should still be there**, and they should be able to try again without creating a duplicate. Test it by turning on airplane mode right after submitting, or with a proxy tool that returns an error. On the web, a broken form that wipes everything after an error is one of the most frustrating bugs a user can meet.

### Session timeout during a long form

Users fill in long forms slowly: they look up their passport number, answer the door, come back an hour later. If the <Term id="session" /> expired meanwhile, the submit fails. Good behavior: warn before the session ends and let the user extend it (WCAG 2.2.1 Timing Adjustable, A), or after logging in again, return to the form **with the data still there**. Bad behavior: a login screen, and then an empty form. Test it by leaving a filled form open past the timeout, or ask a developer for a build with a 1-minute timeout.

### The browser Back button and refresh

- **Back after submit:** going back to a submitted payment or sign up form and submitting again must not create a second order or account.
- **Refresh on the result page:** if the result page was the direct answer to a `POST`, the browser asks "Confirm form resubmission". Good sites redirect after a successful submit, so a refresh is harmless.
- **Back from the next page to fix something:** the form should still be filled in, not empty.

## Security and privacy basics

- **No personal or secret data in URLs.** A form sent with `GET` puts every field in the address as <Term id="query-parameter">query parameters</Term> (`?email=…&phone=…`). URLs end up in browser history, server logs, analytics and shared links. Check the Network tab in <Term id="devtools" />: forms with personal data should use `POST`.
- **Password fields** are masked, have show/hide, allow paste and work with password managers. Details on the [Password Field](/components/password-field) page.
- **Rate limiting on sign up.** Without it, a script can create thousands of fake accounts or flood people's inboxes with confirmation emails. Check for <Term id="rate-limiting" />, a CAPTCHA or email verification, and that the limit is enforced on the server.
- **Consent is opt-in.** Marketing checkboxes start unticked (required under GDPR in the EU), and the Terms checkbox is actually enforced, on the server too. See [Checkbox](/components/checkbox).
- **Input is stored as text, not run as code.** Try `<b>Anna</b>` in a name and check every place it's shown later (see [Security basics](/web/security-basics)).
- **Only collect what's needed.** A newsletter sign up that asks for a date of birth and phone number is a privacy question worth raising.

## Accessibility checklist for forms

Forms are where accessibility problems hurt most: if someone can't submit, they can't buy, book or sign up at all. Use this list together with [Accessibility basics](/web/accessibility-basics):

  ]}
/>

On mobile, run the same checks with VoiceOver and TalkBack (<Term id="screen-reader">screen readers</Term>): every field should announce its label, type, value, hint and error.

## What usually goes wrong

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Valid data rejected** | `O'Brien`, `Đorđe`, `anna+shop@mail.com` or `+44 7700 900123` gets "invalid" | High |
| 2 | **One country's format for all** | UK or Dutch postcodes rejected, US phone format required everywhere | High |
| 3 | **Client-only rules** | The app blocks bad data, but the API accepts it | Medium–High |
| 4 | **Shouting while typing** | "Invalid email" after the first letter | Low–Medium |
| 5 | **Errors by color only** | Red border, no text, nothing for screen readers | Medium–High |
| 6 | **Vague or misplaced errors** | "Error 422" in a toast; the field isn't marked | Medium |
| 7 | **Input lost** | A server error, timeout or Back clears the form | High |
| 8 | **Double submit** | Two accounts or two tickets after a slow response | Medium–High |
| 9 | **Boundary bugs** | 18-year-olds rejected on their birthday, limits off by one | Medium |
| 10 | **Broken autofill** | Values land in the wrong fields, or the form ignores them | Medium |
| 11 | **Focus not managed** | After submit, nothing tells a screen reader user what's wrong | High (for affected users) |
| 12 | **Sensitive data in the URL** | `?email=…&dob=…` visible in the address bar and logs | High (privacy) |

## Example requirements

Here's the spec for the form in the bug hunt below: a sign up form for **Larder**, a grocery delivery app that also sells beer and wine.

<Callout type="example" title="User story: Create a Larder account">

**As a** new customer, **I want to** create an account with my delivery address **so that** I can order groceries to my door.

**Acceptance criteria**

1. Required: full name, email, mobile number, date of birth, password, country, street, town or city, postcode, and accepting the Terms. The marketing opt-in is optional and unticked by default.
2. Names accept any letters, including accents, apostrophes, hyphens and spaces, up to 100 characters. A single name is fine.
3. Any valid email address is accepted, including plus addresses and subdomains. Leading and trailing spaces are removed in every field.
4. Mobile numbers are accepted in international format, with or without spaces.
5. The postcode is checked against the selected country's format (Croatia, Germany, Netherlands, United Kingdom).
6. Users must be **18 or older on the day they sign up**.
7. Errors appear when the user leaves a field or submits, never while they're still typing, and disappear as soon as the value is fixed. Every error has a text message.
8. After a failed submit, an error summary lists all problems and receives focus. Each item moves focus to its field.
9. All fields support AutoFill with the correct autocomplete token.
10. The **Create account** button is disabled while the request is in progress. If the server fails, a clear message appears and **everything the user entered is kept** (except, optionally, the password).

</Callout>

- Type slowly and watch when errors appear.
- Use real-world data: names, emails and phone numbers from the lists above, and a UK postcode.
- Fill the form with AutoFill and look at every field.
- Try dates of birth around the 18th birthday. Today in the demo is **14 May 2026**.
- Submit with mistakes, then use the error summary.
- Make the server fail and submit a valid form.

## How to test a registration form

"How would you test a registration form?" is one of the most common interview tasks, and one of the most common real tasks too. Here's a structure that works for both:

<Steps>

1. **Ask questions first.** Which fields are required? What are the rules for each (length, format, allowed characters)? Which countries and languages? What happens after sign up: a confirmation email, auto login? What if the email is already registered? These questions alone often reveal gaps in the <Term id="acceptance-criteria" />.
2. **Run the happy path end to end.** Sign up with valid data, open the confirmation email, log in with the new account and check that every value was **saved correctly** (on the profile, in emails, in the admin panel or database).
3. **Test each field.** Empty, spaces only, valid and invalid classes (<Term id="equivalence-partitioning" />), minimum, maximum and one beyond (<Term id="boundary-value-analysis" />).
4. **Use real-world data.** Names with apostrophes and accents, plus addresses, international phone numbers, postcodes from each supported country, the 18th birthday, pasted text.
5. **Check validation behavior.** When errors appear, what they say, whether they clear, the error summary, where focus goes, and that nothing typed is lost.
6. **Test the whole form.** Double submit, duplicate email, server error, no connection, session timeout, Back and refresh, closing the app halfway.
7. **Go around the app.** Send the same request with invalid data straight to the API (Postman or DevTools) to prove the server validates too.
8. **Check security and privacy.** No data in the URL, password masked, rate limiting, marketing opt-in unticked, Terms enforced, no account enumeration.
9. **Check accessibility.** Screen reader, keyboard only, large text, contrast, autocomplete tokens.
10. **Repeat on each platform.** Keyboards and AutoFill on iOS and Android, browsers and password managers on the web, small screens and dark mode.

</Steps>

<Callout type="tip" title="In an interview, structure beats volume">

Don't list fifty random checks. Say "I'd ask about the rules first, then group my tests into functional, validation, data, whole-form behavior, server-side, security and accessibility", and give two good examples per group. More on the interview pages: [How would you test a registration form?](/interview/how-to-test-a-registration-form) and [Client-side vs server-side validation](/interview/client-side-vs-server-side-validation).

</Callout>

<Long>

## Test scenarios

### Functional

- Sign up with all valid data; the account is created and every value is saved exactly as entered (after trimming).
- Optional fields can be left empty; required fields can't.
- The confirmation email arrives, and the new account can log in.
- Changing the country updates the postcode rules and re-checks the postcode.
- AutoFill and password managers fill every field correctly.

### Negative

- Submit the empty form: every required field gets a message and the summary lists them all.
- Spaces only in required fields.
- Invalid formats: `anna@`, `anna@@mail.com`, `12abc` as a phone number, `SW1A` as a UK postcode.
- Underage date of birth, impossible date (`31 2 1995`), a date in the future.
- Email already registered (the message follows the spec and doesn't reveal more than intended).
- Terms not accepted.

### Edge cases

- Names: `O'Brien`, `O’Brien` (curly apostrophe), `Đorđe`, `Anne-Marie`, a single name, 100 and 101 characters.
- Emails: plus address, subdomain, 64-character local part, uppercase.
- Phone: with spaces, dashes and brackets, with `00` instead of `+`.
- Postcodes for every supported country, including a leading zero.
- Date of birth: exactly 18 today, 18 tomorrow, 29 February.
- Pasting values with a trailing line break or non-breaking space; emoji in the street name.
- Decimal comma vs point in numeric fields, with the device set to a different region.

### Whole-form behavior

- Double tap and double Enter on submit with a slow network: one account.
- Server returns `500`, `422` or times out: clear message, input kept, retry works.
- Connection lost right after submitting.
- Session expires while the form is open.
- Back after a successful submit, refresh on the result page, Back to fix a value.
- App sent to the background and reopened halfway (see [Background and foreground](/mobile/background-and-foreground)).

### Server-side

- Send the request without the app, with each client rule broken: too long, wrong format, missing required field, extra unknown fields.
- Check that the server trims and normalizes values the same way the app does.
- Many sign ups from one device or IP: rate limit or CAPTCHA kicks in.

### UI and accessibility

- Labels, help text, optional markers and grouping are consistent.
- The right keyboard opens for each field on iOS and Android.
- The focused field and its error are not hidden behind the keyboard.
- Everything from the accessibility checklist above.

## Mobile vs web

<Tabs labels={['Mobile app', 'Website']}>
<Tab>

- **Keyboards:** check the keyboard type, auto-capitalization (on for names, off for emails) and autocorrect (off for names, emails and codes) on each field, with Gboard and Samsung Keyboard on Android.
- **AutoFill:** iOS offers contacts and passwords above the keyboard, Android uses its Autofill service. Test that values land in the right fields and that "Use strong password" works on sign up.
- **The keyboard covers things:** the focused field, its error message and the submit button must not hide behind the keyboard. Scroll the form with the keyboard open.
- **Next and Done keys:** **Next** should move to the next field in order; the last field's **Done** or **Go** should submit or close the keyboard.
- **Interruptions:** a phone call, switching apps to copy a code, or the app being killed in the background should not lose what was typed (see [Interruptions](/mobile/interruptions)).
- **Native pickers:** dates, countries and times often use system pickers. Test them with large text and VoiceOver or TalkBack.
- **Old app versions:** users don't all update. A rule added to the new app version must also exist on the server, or old versions keep sending bad data.

</Tab>
<Tab>

- **Browser autofill and password managers:** Chrome, Safari, Firefox and tools like 1Password should detect every field. In DevTools, check each field's `autocomplete`, `type`, `inputmode` and `name`.
- **Built-in browser validation:** `required` and `type="email"` show the browser's own bubbles, which look different in every browser and can't always be read well. Many teams turn them off and show their own messages. Know which one your app uses.
- **Keyboard only:** Tab through the whole form, select with arrows and Space, submit with Enter. Check the focus ring and that **Enter** doesn't submit twice.
- **Network tab:** check that the form uses `POST`, that no personal data appears in the URL, and what an error response contains.
- **Back, refresh and multiple tabs:** go back after submitting, refresh the result page, open the form in two tabs.
- **Mobile browsers:** the right keyboard depends on `type` and `inputmode`. Test on a real phone, not only in a resized desktop window.
- **Zoom and reflow:** at 200% zoom and at 320 px wide, labels, errors and buttons must stay visible and in order.

</Tab>
</Tabs>

<KeyTakeaways>

- A good form has **visible labels, rules before typing, clear grouping, the right keyboards and autocomplete tokens**.
- **Client-side validation is a convenience, server-side validation is protection.** Test both, and go around the app to prove the server checks.
- Validate **on blur or submit**, not while the user is still typing, and clear errors **as soon as they're fixed**.
- Errors must be **specific, next to the field, not color only, announced to screen readers**, and must never wipe the user's input.
- Test with **real-world data**: apostrophes and accents, plus addresses, international phone numbers, postcodes per country, the 18th birthday, spaces, paste and emoji.
- Test the **whole form**: double submit, server errors, timeouts, Back and refresh, security and accessibility.

</KeyTakeaways>
