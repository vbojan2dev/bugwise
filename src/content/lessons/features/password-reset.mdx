Everyone forgets a password sooner or later: the gym app you haven't opened since January, the airline account you use twice a year. So they tap **Forgot password?**, wait for an email and choose a new password. When that works, nobody notices. When it doesn't, the customer is locked out of their own account, and support gets the call.

Password reset is also a **back door into the account**. Whoever controls the reset link controls the account, no old password needed. That makes it one of the most security-sensitive flows a beginner tester will touch. The good news: most reset bugs are found by simple, careful observation, and you'll find six of them yourself in this lesson.

<Callout type="info" title="Start with login">
This lesson builds on [Login and Sign Up](/features/login-and-sign-up), which explains sessions, tokens and generic error messages. If those words are new, read that page first. Here we go deep on the reset flow only.
</Callout>

## How it works

<ResetFlow />

<Steps>

1. **The user asks for a reset.** They tap **Forgot password?** and enter their email (sometimes a phone number).
2. **The app shows the same confirmation for everyone.** Something like "If an account exists for this email, we've sent a link." It must not say whether the email is registered. Otherwise the reset form becomes a tool for <Term id="account-enumeration" />.
3. **The server creates a token and emails a link.** The token is a long random string, stored on the server with an **expiry time** (often 15 to 60 minutes) and a **used** flag. The link looks like `https://app.example.com/reset?t=8f2a…`.
4. **The user opens the link.** On a phone, a <Term id="deep-link" /> should open the **app's** reset screen. If the app isn't installed, the website opens instead.
5. **The user sets a new password.** The same rules as at sign up apply (for example "at least 8 characters"). Some products also refuse the current password, or recently used ones.
6. **The server finishes the job.** It saves the new password (as a hash, see <Term id="password-hashing" />), marks the token as used, **signs out other sessions** if the spec says so, and sends a "Your password was changed" email so the real owner notices if it wasn't them.

</Steps>

### Several links: which one works?

Users impatiently tap **Send reset link** three times, then open the first email. What should happen? There are two common designs:

| Design | What happens | Why teams choose it |
| --- | --- | --- |
| **Only the latest link works** | Requesting a new link cancels all older ones | Fewer valid keys to the account at the same time. A common choice. |
| **All unexpired links work** | Any link works until it is used or expires; using one cancels the rest | Friendlier when emails arrive out of order |

Neither is "the" right answer. What matters is that the behavior **matches the spec**, and that a link never keeps working after a password was successfully changed. If the spec doesn't say, ask. That question alone often uncovers a missing requirement.

## Example requirements

<Callout type="example" title="User story: Reset a forgotten password">

**As a** PulseFit member who forgot my password, **I want to** reset it from my email **so that** I can get back to my training plan without contacting support.

**Acceptance criteria**

1. After submitting any valid email, the app shows: "If an account exists for this email, we've sent a link to reset your password." Same text, same timing, for registered and unknown emails.
2. Registered emails receive a reset email within 1 minute. The email is trimmed and case-insensitive.
3. The link **expires after 30 minutes** and **works only once**.
4. Requesting a new link **cancels all older links**.
5. The new password follows the sign-up rules (**at least 8 characters**) and must be **different from the current password**.
6. After a successful reset, the user is **signed out on all other devices**, and a "Your password was changed" email is sent.
7. A maximum of **5 reset requests per email per 15 minutes**. After that: "Too many requests, try again later."
8. The email greets the user by name, in the language of their account, contains **no password**, and links to `app.pulsefit.com`.
9. On iOS and Android, the link opens the PulseFit app if it is installed, otherwise the website.

</Callout>

Criterion 7 is <Term id="rate-limiting" />: without it, anyone could flood a person's inbox with reset emails, or hammer the server to test thousands of emails.

### What a good reset email looks like

The email is part of the feature, so test it like a screen. Open it, read every word, and check where the link points.

## What usually goes wrong

| # | Bug | What you see | Typical severity |
| --- | --- | --- | --- |
| 1 | **Account enumeration** | "No account with this email" for unknown emails, "Link sent" for real ones | Medium–High (security) |
| 2 | **Link never expires** | A link from yesterday (or last month) still opens the reset screen | High (security) |
| 3 | **Link works twice** | After resetting, the same link lets you set another password | High (security) |
| 4 | **Old links stay valid** | You requested three links and all three work, although the spec says only the latest | Medium–High |
| 5 | **Password in the email** | "Your password is …" in the email, or the new password repeated in the confirmation | Critical (security) |
| 6 | **Wrong environment in the link** | Link points to `staging.` or `localhost`, or to the website instead of opening the app | High |
| 7 | **Other sessions survive** | After the reset, the old phone or a stolen laptop is still logged in | High (security) |
| 8 | **Password rules not enforced** | The reset screen accepts `abcd` although sign up requires 8 characters | Medium–High |
| 9 | **No rate limit** | You can trigger 100 reset emails in a minute | Medium (security, cost) |
| 10 | **Email problems** | Email never arrives, lands in spam, wrong name or language, broken on mobile mail apps | Medium |
| 11 | **Deep link problems** | Link opens the browser, opens the app's home screen and loses the token, or crashes when the app was closed | Medium–High |
| 12 | **Old password still works** | After a successful reset, both the old and the new password log in | Critical |

<Callout type="bug" title="Why bug #6 happens so often">
Emails are built from templates with a base URL that comes from configuration. Each <Term id="environment" /> (dev, <Term id="staging" />, <Term id="production" />) has its own value, and it's easy to deploy with the wrong one. Always check the **actual link** in the email, not just the button text. Long-press the button on mobile, or hover over it on desktop, to see the real URL.
</Callout>

## Test scenarios

### Functional

- Request a reset for a registered email, receive the email, open the link, set a valid new password.
- **Log in with the new password:** works. **Log in with the old password:** rejected.
- A "Your password was changed" email arrives after the reset.
- The email address is trimmed and case-insensitive: `Maya@Test.com ` works for `maya@test.com`.
- The reset screen shows which account it's for (or at least doesn't let you change someone else's).
- The **back** and **cancel** paths work: leaving the reset screen without saving keeps the old password.

### Negative

- Unknown email: same message, same timing, no email sent. Also check the response in <Term id="devtools" /> or a proxy: the status code and body should look the same too.
- Badly formatted email: `maya@`, `maya.test.com`, empty field.
- **Expired link:** wait (or ask a developer to shorten the expiry on a test environment), then open it.
- **Used link:** reset once, then open the same link again.
- **Older link** after requesting a newer one: does it work? Compare with the spec.
- Tampered link: change one character of the token in the URL. It must fail with a friendly message, not a crash or a 500.
- New password that breaks the rules, confirmation that doesn't match, new password equal to the current one (if required).

### Edge cases

- **Expiry boundaries:** with a 30-minute limit, try at about 29 and 31 minutes. That's <Term id="boundary-value-analysis" /> applied to time.
- **Password length boundaries:** 7, 8 and 9 characters, the maximum and one more.
- Request a reset **while logged in** on another device, then use the link.
- Two resets in parallel: open link A in one browser tab and link B in another, submit both.
- The password is changed via **Settings** (not reset) while a reset link is pending: does the link still work? It usually shouldn't.
- The account is **locked** after too many login attempts: does a successful reset unlock it? Check the spec.
- Social login accounts (Sign in with Apple/Google) that have no password: what does reset do for them?
- Unicode and special characters in the new password; a password set on the web must also work in the app.

### UI & usability

- The confirmation message tells the user what to do next ("check your inbox and spam folder").
- Password rules are visible **before** typing; a show/hide button exists; <Term id="password-manager">password managers</Term> offer to save the new password.
- Expired and used links show a **clear message with a "Request a new link" button**, not a blank page or "Error 400".
- The email looks right in common mail apps (Gmail, Outlook, Apple Mail) on phone and desktop, in light and dark mode.
- The email is in the **account's language** and uses the right name.

### Security basics

These are defensive checks you can do with no special skills:

- Generic message for every email (no <Term id="account-enumeration" />).
- Link expires, works once, and older links behave as specified.
- **No password** in any email, ever. Not the old one, not the new one.
- The token is long and random (not `?user=123` or the email address), and the link uses `https`.
- After the reset, **other sessions are signed out** (if specified) and the old password stops working everywhere.
- Rate limit on reset requests is enforced on the server (reloading or reinstalling doesn't reset it).
- The link points to the correct **environment** and domain.

<Callout type="warning" title="Stay on your test environment">
Only test reset flows on accounts and environments you're allowed to test. Use your own test email addresses (many teams use a shared test inbox or plus addressing like `qa+reset1@company.com`), never real customers' emails.
</Callout>

### Accessibility

- Fields have labels, errors are announced by a <Term id="screen-reader" />, and the confirmation message is announced too.
- No short time limit on the reset screen itself (the link may expire, but the form shouldn't time out while someone types).
- The email works with a screen reader: the button is a real link with a meaningful name ("Reset password", not "Click here").

## Mobile vs web

<Tabs labels={['Mobile app', 'Website']}>
<Tab>

- **Deep links:** tap the link in the Mail app and in Gmail. With the app installed it should open the app's reset screen (iOS Universal Links, Android App Links; see [Deep links](/features/deep-links)). Test with the app **not installed**, **closed**, **in the background**, and **logged in as someone else**. See [Interruptions](/mobile/interruptions) for switching between apps.
- **In-app browsers:** Gmail and Outlook may open links in their own browser instead of your app. The website fallback must work there too.
- **Read the email on the same phone:** switching from the app to the mail app and back must not lose what the user typed.
- **Password managers:** after the reset, iOS Passwords or Google Password Manager should offer to update the saved password.
- **Biometrics:** if Face ID or fingerprint unlocks a saved password, it must not keep logging in with the old one after a reset.
- **Other devices:** keep a second phone or tablet logged in and check it gets signed out.

</Tab>
<Tab>

- **Open the link in a different browser** than the one that requested it, and in a private window. It should still work (the token is in the link, not in a cookie).
- **Network tab:** in <Term id="devtools" />, check the reset request is a `POST`, the response doesn't reveal whether the email exists, and the token never appears in third-party requests (analytics, ads).
- **Back button:** after a successful reset, pressing Back must not let you submit the form again.
- **Other tabs:** a second tab logged in as the same user should be signed out after the reset (if specified).
- **Email preview:** desktop mail clients and webmail render HTML differently. Check the button and the plain link both work.
- **Cross-browser:** the reset page works in Chrome, Safari and Firefox, including autofill of the new password.

</Tab>
</Tabs>

<KeyTakeaways>

- A reset link is a **temporary key to the account**: it must be random, **expire**, work **once**, and older links must behave exactly as the spec says.
- Show the **same message** for every email, so the reset form can't be used to find out who has an account.
- Test the **email like a screen**: no passwords, right name and language, and a link to the **right environment**.
- After a reset: the **new password works, the old one doesn't**, other sessions are signed out, and a "password changed" email arrives.
- On mobile, check **deep links** with the app installed, closed and missing; on the web, check other tabs and the Network panel.

</KeyTakeaways>
